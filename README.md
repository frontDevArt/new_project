# listam — мониторинг list.am под заявки покупателей

Инструмент брокера: копим объявления о продаже квартир, чтобы под заявку клиента
находить вариант первыми. Полная спека и роадмап — в файле
`list.am → заявки покупателей MVP-спека и роадмап.md`.

Этапы **M0 и M1 закрыты** (21.09.2026). M0 — каркас, порты, схема базы, выгрузка,
`doctor`, доступ к сайту через браузер, парсер карточек ленты, прогон `scrape`
и пересчёт `recheck`; разбор QA-аудита:
`docs/superpowers/plans/2026-09-21-m0-qa-fixes.md`. M1 — инкрементальный обход
`scrape --fresh`, пометка снятых объявлений, счётчик сменивших цену и команда
`changes`; план и отчёты по фазам:
`docs/superpowers/plans/2026-09-21-m1-delta-and-history.md`.

Критерий M1 предъявлен на живой ленте: полный обход прошёл 215 страниц за 11 минут,
следующий за ним `scrape --fresh` через час — **6 страниц вместо 215**, и принёс
только новое. Схема базы — версия 4, батарея — 363 passed, 12 skipped.
Дальше M2: заявки и матчинг.

## Быстрый старт

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt -r requirements-playwright.txt
.venv/Scripts/python -m playwright install chromium
cp .env.example .env
.venv/Scripts/python -m listam doctor
```

## Команды

| Команда | Что делает |
| --- | --- |
| `python -m listam doctor` | Проверяет конфиг, хранилище, схему базы, курс, права на запись и доступ к list.am |
| `python -m listam doctor --no-network` | То же, но без сетевых проверок |
| `python -m listam scrape` | Проходит по ленте категории и обновляет базу |
| `python -m listam scrape --fresh` | Инкрементальный обход: идёт с головы ленты и встаёт, когда подряд пройдено `scrape.fresh_stop_after_known_pages` страниц без новых объявлений |
| `python -m listam scrape --max-pages 5` | То же, но не дальше пятой страницы (иначе число берётся из конфига) |
| `python -m listam scrape --dry-run` | Разбирает страницы и печатает счётчики; файла базы не создаёт и в хранилище не ходит |
| `python -m listam scrape --allow-shrink` | Разрешает заливку, даже если база заметно усохла |
| `python -m listam scrape --resume` | Продолжает прерванный обход со следующей после пройденной страницы; если прошлый обход завершён без ошибок — идёт с первой |
| `python -m listam scrape --allow-upload-with-errors` | Заливает базу в хранилище, даже если в прогоне были ошибки |
| `python -m listam recheck` | Пересчитывает пометки и суммы в валюте оригинала по всей базе: разовая операция после смены правил или схемы |
| `python -m listam export` | Выгружает текущую базу в `.xlsx` |
| `python -m listam changes` | Печатает, что принёс последний прогон: новое, сменившее цену, снятое |
| `python -m listam changes --hours 24` | То же, но за последние сутки, а не с начала прошлого прогона |
| `python -m listam changes --limit 20` | Не больше 20 строк в каждом разделе (по умолчанию — `changes.limit` из конфига) |

Окружение выбирается переменной `APP_ENV` (`dev` по умолчанию) или флагом `--env`.

Что сейчас в базе (21.09.2026, после полного и инкрементального прогонов M1):
20 798 объявлений — 20 636 активных и 162 снятых с публикации, из них помечено
аномалией 24. Медиана по базе **без помеченных** — 2153 $/м² и 160 000 $ за квартиру
(20 716 строк с ценой за метр). Валюты: USD 18 748, AMD 1992, EUR 55, RUB 3 —
у евро и рублей пересчитанных колонок нет, но сумма лежит в «Цене в валюте».
Продавцы: агентства 16 666, собственники 4132. Точек в `price_history` — 20 867.
Медианы по районам — в плане M0.

Прогон устроен так.

1. **Курс — предусловие, а не счётчик.** Он берётся до того, как тронута база.
   Не получен — прогон не начинается вовсе: ни строки в `listings`, ни точки в
   `price_history`, код возврата 1. Иначе сбой курса стёр бы пересчитанные цены
   по всей базе. По той же причине пустой пересчёт никогда не затирает уже
   посчитанное: `None` значит «не смог», а не «цены больше нет». Исключение —
   смена валюты или сырой цены: тогда старый пересчёт относится к прошлой цене,
   и `price_usd`, `price_amd`, `price_per_sqm` переписываются безусловно,
   включая пустыми. Иначе карточка, переехавшая из `100,000 $` в `90,000 €`,
   так и стояла бы в выгрузке со старой долларовой ценой.
   Сумма в валюте оригинала лежит отдельно, в `listings.price_amount`: курсов
   EUR и RUB мы не выдумываем, пересчитанные колонки у таких цен пустые, но
   само число не теряется — в `.xlsx` оно видно в колонке «Цена в валюте»
   (колонок 22, автофильтр `A1:V`).
2. **Локальная копия сверяется с удалённой.** Берётся та, по которой прогон
   ходил позже. Без этого вторая машина или откат папки `data/` затирали бы
   общую базу старым снимком.
3. **Прогон в доме один.** На время обхода рядом с базой лежит файл-замок
   (`listam.lock`): второй `scrape` не начинается, а честно говорит, что
   первый ещё идёт. Иначе две копии базы расходятся, и побеждает та, что
   позже залилась в хранилище. Замок старше `storage.lock_stale_seconds`
   считается брошенным (прогон убили) и перехватывается. Чтобы этот
   срок не срабатывал под живым прогоном (215 страниц с паузой — это часы),
   замок переписывается после каждой пройденной страницы: срок — защита от
   убитого процесса, а не от долгого. Отпускается замок при любом исходе
   прогона, включая падение подготовки: недоступный файл базы — это ошибка
   прогона с внятным текстом, а не запертая навсегда папка.
   Падение прогона — тоже прогон: любое исключение, включая `Ctrl+C`, попадает
   в `runs.errors` и `runs.notes` и только потом летит наружу. Половинная база
   не притворяется удачным обходом.
4. Страницы идут по путевой пагинации с паузой `scrape.delay_seconds`.
   Страница, отдавшая меньше `scrape.min_cards_per_page` карточек, считается
   сбоем: так выглядит смена вёрстки и заглушка Cloudflare, отданная с кодом
   200. Обход в этом случае встаёт. Сверху есть такой же порог
   `scrape.max_cards_per_page`: столько карточек лента не отдаёт, и если их
   больше — в разбор попала не она. Лента ищется только в контейнере
   `#contentr`; нет контейнера — прогон встаёт с ошибкой «контейнер ленты
   не найден», а не собирает ссылки `/item/` из шапки и подвала, выдавая
   пяток карточек-огрызков за страницу. Если пройдена всего одна страница, а
   `max_pages` не равен 1 — это тоже сбой: пагинатор не дал следующей.
   Сверху есть потолок `scrape.hard_page_limit`: зацикленный пагинатор не
   имеет права крутить обход бесконечно. Номер каждой пройденной страницы
   уходит в `runs.last_page` — со следующей за ней продолжает `scrape --resume`
   (сама она уже разобрана и записана). Продолжать можно только прерванный
   обход: после прогона, дошедшего до конца без ошибок, `--resume` идёт с первой
   страницы и пишет об этом в `runs.notes`, а не проходит одну последнюю
   страницу, отчитываясь успехом.
   Полнота обхода проверяется двумя порогами: `scrape.expected_pages_min`
   (явное число страниц, `null` — проверки нет) и `scrape.max_pages_drop_percent`
   (насколько обход может быть короче прошлого удачного прогона). Обход,
   вставший на второй странице из-за пропавшего пагинатора, — это сбой, а не
   короткий прогон. С `--max-pages` и `--resume` проверка не применяется:
   там обход укорочен нарочно.
5. **Инкрементальный обход знает, где голова ленты кончилась.** `scrape --fresh`
   идёт с первой страницы и считает страницы, на которых не встретилось ни одного
   нового объявления. Набралось `scrape.fresh_stop_after_known_pages` таких подряд —
   обход встал: дальше идёт то, что уже лежит в базе. Порог не «первый известный ID»,
   как в спеке: лента переставляет объявление наверх при поднятии, первое известное
   попадается на первой же странице почти всегда, и обход вставал бы, не дойдя до
   настоящего нового. Две страницы — это около 190 карточек запаса.
   Сверху есть потолок `scrape.fresh_max_pages`. Упёрлись в него — это **ошибка**
   прогона, а не успех: до известных объявлений обход не дошёл, значит часть ленты
   он не видел и нужен полный обход. Молча укоротить ленту нельзя.
   Режим прогона пишется в `runs.mode`: `full` (без ограничений), `partial`
   (`--max-pages`), `resume` (`--resume`), `fresh` (`--fresh`). Меркой полноты для
   следующего обхода (проверка недобора страниц из пункта 4) считается **только**
   `full` — иначе инкрементальный прогон на шести страницах стал бы нормой и
   проверка замолчала бы. `--fresh` и `--resume` вместе не работают: одно идёт
   с головы ленты, другое продолжает прерванный полный обход, и командная строка
   отвечает отказом с кодом возврата 2.

6. Каждая карточка кладётся апсертом и проверяется на мусор (секция `validate`):
   сработавшие правила уходят в `listings.anomaly`, объявление сохраняется как
   есть, но в медианы не идёт и в `.xlsx` получает колонку «Сомнительно».
   Пороги из конфига накладываются на значения по умолчанию по одному:
   `validate: {price_usd: {min: 1000}}` меняет нижнюю границу и оставляет
   верхнюю на месте, а не стирает её вместе со всем правилом.
7. Точка в `price_history` ставится, только когда изменилась **сырая** цена
   (`price_raw` или `currency`), и уносит с собой курс прогона. Пересчитанные
   `price_usd`, `price_amd`, `price_per_sqm` содержательным изменением карточки
   не считаются — иначе каждое движение курса выглядело бы как смена цены у
   всей базы разом.
8. **Ушедшее с ленты помечается снятым.** После обхода активные объявления
   сверяются с тем, что встретилось на ленте; пропавшее получает `status='gone'`
   и дату в `listings.gone_at`. Помечает **только полный удачный обход**
   (`mode == "full"`, `errors == 0`): инкрементальный, укороченный и продолженный
   видели не всю ленту, и «не встретилось» у них не значит «снято».
   У пометки есть порог `scrape.max_gone_percent`: пропало больше этой доли
   активных — не помечаем ничего, считаем ошибкой прогона и пишем об этом
   в `runs.notes`. Так выглядит оборванный обход или уехавшая вёрстка, а не рынок.
   Дата снятия живёт в отдельной колонке, а не выводится из `last_seen`:
   `last_seen` двигает каждый прогон, а вернувшееся объявление обязано забыть дату
   снятия. Вернулось на ленту — снова `status='active'`, `gone_at = NULL`,
   `first_seen` не трогается: это то же объявление, а не новое.
   Снятое остаётся в базе и в выгрузке — цена снятой квартиры это история рынка,
   и на M2 по ней считаются медианы кластеров.

9. **Вёрстка уехала — это видно.** Прогон считает, у какой доли карточек
   заполнено поле, и сравнивает с порогами секции `coverage`: переименованный
   класс `ge3` делает всю базу собственниками, пропавший класс района —
   базой без районов. Выход за порог — ошибка прогона с внятным текстом.
   На выборке меньше `coverage.min_sample` доля ничего не значит, и проверка
   не выносит приговора — но и не молчит: в `runs.notes` уходит строка
   «проверка вёрстки пропущена». Прогон, который вёрстку не проверял, не
   должен выглядеть как прогон, у которого всё в порядке. Пороги здесь тоже
   накладываются по одному: названный в конфиге `min_filled` не уносит
   соседний `min_share`.
10. **Ошибка отменяет заливку.** В хранилище лежит общая копия базы; прогон,
   у которого `errors > 0`, записал неполную картину, и залить её означает
   испортить ту, что была в порядке. Поэтому при любой ошибке не выполняются
   ни ротация копий, ни заливка: локальная копия остаётся на диске — посмотри
   её глазами и, если всё в порядке, `scrape --allow-upload-with-errors`.
   Заливка, срезающая число объявлений больше чем на `storage.max_shrink_percent`,
   не выполняется без `--allow-shrink`. Перед заливкой прежняя копия базы
   кладётся в хранилище под именем с отметкой времени; держим
   `storage.keep_backups` последних. Чистка считает своими только копии базы —
   те, у которых расширение базы и отметка времени, поставленная самой
   ротацией. Выгрузка `listam-20260921-0937.xlsx`, лежащая в том же хранилище,
   под чистку не попадает и места в счёте `keep_backups` не занимает.
11. **Уезжает снимок, а не файл базы.** База живёт в режиме WAL: свежие записи
   лежат в соседнем `-wal`, пока их не перенесли в основной файл. Копировать
   основной файл, пока базу держит открытой второй читатель, означает иногда
   залить копию без последнего прогона. Поэтому заливается снимок
   (`VACUUM INTO` во временный файл рядом с базой) — он целен всегда.
   Снимок не сделался — это ошибка прогона и отказ от заливки. Скачанная из
   хранилища база приходит без спутников: `-wal` и `-shm` от прежнего файла
   убираются, чтобы SQLite не принял их за свои.

`recheck` — не прогон: он не ходит на сайт и ничего не узнаёт о рынке. Он берёт
тот же замок, накатывает миграции и пересчитывает по всем строкам то, что
считается из уже записанного: пометку `anomaly` и сумму в валюте оригинала.
Цены, даты и историю он не трогает — `last_seen` не двигается, потому что
карточку никто не видел. Нужен он тогда, когда правила проверки или схема
изменились после того, как база была набрана: прогон по ленте чинит только те
карточки, что встретил сегодня, а снятая с публикации не встретится уже никогда.
Пересчитанная копия уезжает в хранилище по тем же правилам, что у прогона.

`export` ничего не мигрирует: он читает базу, а не чинит её. Схема младше той,
которую ждёт код, — внятная ошибка и код возврата 1, а не тихая правка общей
базы по дороге к таблице.

`changes` живёт по тем же правилам: он не ходит на сайт, не берёт замок и
ничего не мигрирует — только читает. Отметка, с которой считается дельта, по
умолчанию берётся из журнала: это начало последнего прогона, то есть «что
принёс последний обход». Новым считается то, у чего `first_seen` позже отметки,
снятым — то, у чего позже `gone_at`; сменившим цену — точка в `price_history`,
у которой есть предыдущая. Первая точка объявления сменой цены не считается:
это появление, а не подешевело.

Ошибки прогона попадают в `runs.errors` и `runs.notes`, а ненулевой счётчик
ошибок — в код возврата 1. Нулевой итог прогона никогда не даёт 0.

База открывается в режиме WAL и с `storage.busy_timeout_ms`: `export` читает
её, пока прогон пишет, а не падает с «database is locked». Схема меняется
только версионированной миграцией, и каждая накатывается одной транзакцией —
падение посреди неё не оставляет половину схемы.

## Как запускать по расписанию

Планировщик живёт в системе, а не в инструменте: своего демона у `listam` нет
и не будет. Расписание двухслойное.

* **Инкрементальный обход — раз в час.** `scrape --fresh` проходит единицы
  страниц и приносит то, что появилось за час. Это дежурный режим.
* **Полный обход — раз в сутки.** Только он проверяет ленту целиком и потому
  только он имеет право помечать снятые (пункт 8) и быть меркой полноты для
  проверки недобора страниц (пункты 4 и 5). Час-полтора в сутки — его цена.

Накладываться они не могут: замок прогона (пункт 3) не пускает второй `scrape`,
пока идёт первый. Если часовой запуск пришёлся на середину суточного, он честно
скажет, что прогон уже идёт, и уйдёт ни с чем — это нормально, следующий придёт
через час.

Windows, `schtasks` (обход идёт через браузер с окном, поэтому задача ставится
на вход пользователя, а не на `SYSTEM`):

```bat
schtasks /create /tn "listam-fresh" /sc hourly /ru "%USERNAME%" /it ^
  /tr "C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam scrape --fresh"
schtasks /create /tn "listam-full" /sc daily /st 04:00 /ru "%USERNAME%" /it ^
  /tr "C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam scrape"
```

Сервер без экрана, `cron` — браузер заворачивается в виртуальный экран
(`headless: false` трогать нельзя, см. «Как обходится Cloudflare»):

```cron
0 * * * *  cd /srv/listam && xvfb-run -a .venv/bin/python -m listam scrape --fresh
0 4 * * *  cd /srv/listam && xvfb-run -a .venv/bin/python -m listam scrape
```

Ненулевой код возврата — повод посмотреть `runs.notes` за этот прогон:
там лежит и причина остановки, и отказ от пометки снятых, и отказ от заливки.

## Устройство

```
listam/
  ports/        интерфейсы: Storage, Database, Fetcher, RateProvider, Exporter,
                RequestsSource, Notifier
  adapters/     реализации: local/gdrive, sqlite, playwright/http/files,
                rate_am/fixed, xlsx_local
  domain/       модель данных, разбор цен, проверки и доли заполненности
  migrations/   версионированные миграции схемы
  wiring.py     единственное место, где код знает имена адаптеров
  doctor.py     самопроверка окружения
  cli.py        командная строка
config/         dev.yaml, prod.yaml — без секретов
tests/          контрактные тесты на каждый порт + тесты домена
```

Правило, которое держит переносимость: ни один аккаунт, путь, ключ и идентификатор
файла не зашит в код. Всё внешнее — за портом, выбор реализации — в конфиге,
секреты — только в `.env`.

## Переезд на другой аккаунт или хранилище

1. Скопировать `data/listam.sqlite` в новое хранилище — база это один файл.
2. Заполнить `.env` новыми идентификаторами (образец — `.env.example`).
3. Переключить `storage.kind` в нужном `config/<env>.yaml`.
4. `APP_ENV=prod python -m listam doctor` — отчёт должен быть без строк «СБОЙ».

Для Google Drive дополнительно: `pip install -r requirements-gdrive.txt`, сервисный
аккаунт с ключом в JSON, папка Drive расшарена на адрес сервисного аккаунта с правом
редактирования. `GDRIVE_FOLDER` — идентификатор папки, `GDRIVE_CREDENTIALS_FILE` —
путь к ключу.

## Как обходится Cloudflare

Перед list.am стоит проверка Cloudflare: на обычный HTTP-запрос сайт отвечает
`403` с заголовком `Cf-Mitigated: challenge`. Поэтому страницы берёт настоящий
браузер — адаптер `playwright` порта `Fetcher` (`scrape.kind: playwright`).

Что выяснилось на живом сайте 21.09.2026:

| Как ходим | Что отдаёт list.am |
| --- | --- |
| `requests` | 403, проверка Cloudflare |
| Playwright, headless | 403 — headless отличают и режут |
| Playwright, headed, без флага ниже | первая страница 200, вторая и дальше 403 |
| Playwright, headed, с флагом | 200 на все страницы подряд |

Отсюда две настройки, которые нельзя трогать не подумав:

* `headless: false` — браузер запускается с окном. На сервере без экрана его
  заворачивают в виртуальный: `xvfb-run -a python -m listam doctor`.
* флаг `--disable-blink-features=AutomationControlled` — без него Chromium
  сообщает странице, что им управляет автоматика. Флаг в коде адаптера, не в
  конфиге: это не вкус, а условие работы.

`profile_dir` (по умолчанию `./data/browser`) держит профиль браузера между
запусками, чтобы не проходить проверку каждый раз заново. Профиль иногда
протухает — сохранённое состояние перестаёт годиться, и проверка начинает
приходить на каждую страницу. Адаптер это распознаёт и один раз за прогон
сносит профиль, начиная с чистого листа; в логе это видно как успешный
повтор после сбоя.

Сносит он при этом только свой каталог — тот, который сам завёл и пометил
изнутри. И `profile_dir`, накрывающий рабочую папку (`storage.work_dir`,
`storage.directory`, `scrape.pages_dir`, `export.path`), прогон не запускает
вовсе: опечатка `profile_dir: ./data` иначе унесла бы базу. `storage.directory`
в этом списке не зря: при `storage.kind: local` это и есть хранилище — общая
копия базы и все её бэкапы.

Если проверка не проходит и с браузером, помогает другой адрес: армянский
домашний интернет или VPS. Cloudflare включает проверку в том числе по
репутации IP.

### Когда сайта под рукой нет

У порта `Fetcher` есть реализация `files`: она читает страницы с диска тем же
кодом, каким читала бы ленту. Нужна, чтобы переразобрать старый снимок после
правки парсера, не трогая сайт, — и чтобы работать с сохранённой вручную
страницей. Переключается `scrape.kind: files`, страницы лежат в
`data/pages/`, имя файла получается из пути URL: `/category/60/2` →
`category-60-2.html`. Подробности — в `docs/сохранённые-страницы.md`.

## Тесты

```bash
.venv/Scripts/python -m pytest -q
```

Контрактные тесты (`tests/contracts/`) написаны против портов: подменили
реализацию — тест обязан пройти без изменений. Батарея порта `Fetcher` гоняется
на всех трёх реализациях, включая `playwright` — он ходит в локальный тестовый
сервер, а не на list.am. Тесты gdrive пропускаются, пока не заданы
`GDRIVE_FOLDER` и `GDRIVE_CREDENTIALS_FILE`; тесты playwright — пока не
установлен пакет.
