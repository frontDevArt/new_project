# listam — мониторинг list.am под заявки покупателей

Инструмент брокера: копим объявления о продаже квартир, чтобы под заявку клиента
находить вариант первыми. Полная спека и роадмап — в файле
`list.am → заявки покупателей MVP-спека и роадмап.md`.

Этапы **M0 и M1 закрыты** (22.09.2026, M1 — после разбора строгого QA-аудита).
M0 — каркас, порты, схема базы, выгрузка, `doctor`, доступ к сайту через
браузер, парсер карточек ленты, прогон `scrape` и пересчёт `recheck`; разбор
QA-аудита: `docs/superpowers/plans/2026-09-21-m0-qa-fixes.md`. M1 —
инкрементальный обход `scrape --fresh`, пометка снятых объявлений, возврат
объявления на ленту, счётчик сменивших цену и команда `changes`; план и отчёты
по фазам: `docs/superpowers/plans/2026-09-21-m1-delta-and-history.md`, разбор
QA-аудита (13 находок, пять фаз):
`docs/superpowers/plans/2026-09-21-m1-qa-fixes.md`.

Критерий M1 предъявлен на живой ленте: полный обход прошёл 215 страниц за
11 минут, следующий за ним `scrape --fresh` через час — единицы страниц вместо
215, и принёс только новое. Главное, что починил разбор аудита: раздел «Снято»
в `changes` переживает часовые инкрементальные прогоны — раньше при расписании,
которое README сам и предлагает, человек не увидел бы снятых **никогда**.
**M2 в работе** (план и отчёты по фазам:
`docs/superpowers/plans/2026-09-22-m2-requests-and-matching.md`, спека рядом
в `docs/superpowers/specs/`). Написано и закрыто тестами всё: заявка как
сущность, источник заявок (`csv` и Google Sheet), кластеры-дубли, движок
скоринга, запись матчей и витрина — команды `requests`, `cluster`, `match`,
`matches` и лист «Матчи» в выгрузке. Осталась боевая приёмка на живой базе:
до неё `data/listam.sqlite` остаётся на схеме 6 и ничем из M2 не тронута.
Схема кода — версия **7**, батарея — **602 passed, 18 skipped**.

## Быстрый старт

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt -r requirements-playwright.txt
.venv/Scripts/python -m playwright install chromium
cp .env.example .env
.venv/Scripts/python -m listam doctor
```

## Команды

| Команда | Что делает |
| --- | --- |
| `python -m listam doctor` | Проверяет конфиг, хранилище, схему базы, курс, права на запись и доступ к list.am |
| `python -m listam doctor --no-network` | То же, но без сетевых проверок |
| `python -m listam scrape` | Проходит по ленте категории и обновляет базу |
| `python -m listam scrape --fresh` | Инкрементальный обход: идёт с головы ленты и встаёт, когда подряд пройдено `scrape.fresh_stop_after_known_pages` страниц без новых объявлений |
| `python -m listam scrape --max-pages 5` | То же, но не дальше пятой страницы (иначе число берётся из конфига) |
| `python -m listam scrape --dry-run` | Разбирает страницы и печатает счётчики; файла базы не создаёт и в хранилище не ходит |
| `python -m listam scrape --allow-shrink` | Разрешает заливку, даже если база заметно усохла |
| `python -m listam scrape --resume` | Продолжает прерванный обход со следующей после пройденной страницы; если прошлый обход завершён без ошибок — идёт с первой |
| `python -m listam scrape --allow-upload-with-errors` | Заливает базу в хранилище, даже если в прогоне были ошибки |
| `python -m listam recheck` | Пересчитывает пометки и суммы в валюте оригинала по всей базе: разовая операция после смены правил или схемы |
| `python -m listam export` | Выгружает текущую базу в `.xlsx` |
| `python -m listam requests` | Читает заявки покупателей из источника (`csv` или Google Sheet) и кладёт разобранное в базу |
| `python -m listam cluster` | Пересчитывает кластеры-дубли по всей базе: одна квартира, выставленная тридцать раз, — это один вариант |
| `python -m listam match --all` | Подбирает объявления по всей базе под все активные заявки |
| `python -m listam match --new` | То же, но только по тому, что тронулось с начала прошлого прогона: появилось, вернулось на ленту или сменило цену |
| `python -m listam match --request R-1` | То же по одной названной заявке |
| `python -m listam matches` | Витрина: что подобралось, от лучшего балла к худшему |
| `python -m listam matches --request R-1` | Только по одной заявке |
| `python -m listam matches --limit 20 --min-score 70` | Не больше 20 строк и только от 70 баллов (по умолчанию — `match.limit` и `match.thresholds.digest` из конфига) |
| `python -m listam matches --new` | Срез «что нового со вчера»: появилось, подешевело, вернулось; отпавшее — строкой внизу раздела |
| `python -m listam notify --hot` | «Звони сейчас»: что появилось выше порога `match.thresholds.hot`, с прошлой отправки |
| `python -m listam notify --digest` | Дневная сводка: всё, что тронулось с прошлой отправки дайджеста |
| `python -m listam notify --feed` | Что пришло на ленту вне заявок: счётчики и лучшие по выгодности |
| `python -m listam notify --digest --dry-run` | Показать, что было бы послано, и не посылать; журнал не трогается |
| `python -m listam changes` | Печатает, что принёс последний прогон: новое, сменившее цену, снятое, вернувшееся |
| `python -m listam changes --hours 24` | То же, но за последние сутки, а не с начала прошлого прогона (одно окно на все четыре раздела) |
| `python -m listam changes --limit 20` | Не больше 20 строк в каждом разделе (по умолчанию — `changes.limit` из конфига) |

Бессмысленный ввод команда отклоняет **на входе**, а не истолковывает:
`--max-pages 0`, `--max-pages -1`, `--hours -5`, `--limit 0`, `--limit -1`,
`--min-score 120`, `match --new --all` и `match` без единого флага —
это отказ с кодом возврата 2 и внятным текстом. До базы и до сайта дело не
доходит вовсе. Раньше `--max-pages 0` превращался в полный обход на 215 страниц
(ноль съедало `if limit`), `--hours -5` брал окно в будущем, а `--limit 0`
печатал «…и ещё 7» вместо строк.

Окружение выбирается переменной `APP_ENV` (`dev` по умолчанию) или флагом `--env`.

Что сейчас в базе (22.09.2026, после полного обхода на починенном коде):
20 819 объявлений — 20 612 активных и 207 снятых с публикации, из них помечено
аномалией 24. Медиана по базе **без помеченных** — 2153 $/м² и 160 000 $ за квартиру
(20 735 строк с ценой за метр). Валюты: USD 18 765, AMD 1994, EUR 56, RUB 4 —
у евро и рублей пересчитанных колонок нет, но сумма лежит в «Цене в валюте».
Продавцы: агентства 16 678, собственники 4141. Точек в `price_history` — 20 913.
Медианы по районам — в плане M0.

Прогон устроен так.

1. **Курс — предусловие, а не счётчик.** Он берётся до того, как тронута база.
   Не получен — прогон не начинается вовсе: ни строки в `listings`, ни точки в
   `price_history`, код возврата 1. Иначе сбой курса стёр бы пересчитанные цены
   по всей базе. По той же причине пустой пересчёт никогда не затирает уже
   посчитанное: `None` значит «не смог», а не «цены больше нет». Исключение —
   смена валюты или сырой цены: тогда старый пересчёт относится к прошлой цене,
   и `price_usd`, `price_amd`, `price_per_sqm` переписываются безусловно,
   включая пустыми. Иначе карточка, переехавшая из `100,000 $` в `90,000 €`,
   так и стояла бы в выгрузке со старой долларовой ценой.
   Сумма в валюте оригинала лежит отдельно, в `listings.price_amount`: курсов
   EUR и RUB мы не выдумываем, пересчитанные колонки у таких цен пустые, но
   само число не теряется — в `.xlsx` оно видно в колонке «Цена в валюте»
   (колонок 22, автофильтр `A1:V`).
2. **Локальная копия сверяется с удалённой.** Берётся та, по которой прогон
   ходил позже. Без этого вторая машина или откат папки `data/` затирали бы
   общую базу старым снимком.
3. **Прогон в доме один.** На время обхода рядом с базой лежит файл-замок
   (`listam.lock`): второй `scrape` не начинается, а честно говорит, что
   первый ещё идёт. Иначе две копии базы расходятся, и побеждает та, что
   позже залилась в хранилище. Замок старше `storage.lock_stale_seconds`
   считается брошенным (прогон убили) и перехватывается. Чтобы этот
   срок не срабатывал под живым прогоном (215 страниц с паузой — это часы),
   замок переписывается после каждой пройденной страницы: срок — защита от
   убитого процесса, а не от долгого. Отпускается замок при любом исходе
   прогона, включая падение подготовки: недоступный файл базы — это ошибка
   прогона с внятным текстом, а не запертая навсегда папка.
   Падение прогона — тоже прогон: любое исключение, включая `Ctrl+C`, попадает
   в `runs.errors` и `runs.notes` и только потом летит наружу. Половинная база
   не притворяется удачным обходом.
4. Страницы идут по путевой пагинации с паузой `scrape.delay_seconds`.
   Страница, отдавшая меньше `scrape.min_cards_per_page` карточек, считается
   сбоем: так выглядит смена вёрстки и заглушка Cloudflare, отданная с кодом
   200. Обход в этом случае встаёт. Сверху есть такой же порог
   `scrape.max_cards_per_page`: столько карточек лента не отдаёт, и если их
   больше — в разбор попала не она. Лента ищется только в контейнере
   `#contentr`; нет контейнера — прогон встаёт с ошибкой «контейнер ленты
   не найден», а не собирает ссылки `/item/` из шапки и подвала, выдавая
   пяток карточек-огрызков за страницу. Если пройдена всего одна страница, а
   `max_pages` не равен 1 — это тоже сбой: пагинатор не дал следующей.
   Сверху есть потолок `scrape.hard_page_limit`: зацикленный пагинатор не
   имеет права крутить обход бесконечно. Номер каждой пройденной страницы
   уходит в `runs.last_page` — со следующей за ней продолжает `scrape --resume`
   (сама она уже разобрана и записана). Продолжать можно только прерванный
   обход: после прогона, дошедшего до конца без ошибок, `--resume` идёт с первой
   страницы и пишет об этом в `runs.notes`, а не проходит одну последнюю
   страницу, отчитываясь успехом.
   **`--resume` продолжает обход, а не строку журнала.** Меркой берётся не
   последний `full`, а последний прогон **того же обхода**: `full` и все
   продолжающие его `resume`, из них — максимальный `last_page`. Иначе второй
   `--resume` откатывался бы на страницу первого: полный встал на 100-й,
   продолжение дошло до 150-й — и следующий шёл бы снова со 101-й, выбрасывая
   полсотни пройденных страниц. Отдаётся при этом строка **последнего** прогона
   обхода, а не самого `full`: по ней видно, закрыт обход или оборвался — иначе
   обход, доведённый до конца продолжением, всегда выглядел бы незакрытым.
   Полнота обхода проверяется двумя порогами: `scrape.expected_pages_min`
   (явное число страниц, `null` — проверки нет) и `scrape.max_pages_drop_percent`
   (насколько обход может быть короче прошлого удачного прогона). Обход,
   вставший на второй странице из-за пропавшего пагинатора, — это сбой, а не
   короткий прогон. С `--max-pages` и `--resume` проверка не применяется:
   там обход укорочен нарочно.
5. **Инкрементальный обход знает, где голова ленты кончилась.** `scrape --fresh`
   идёт с первой страницы и считает страницы, на которых не встретилось ни одного
   нового объявления. Набралось `scrape.fresh_stop_after_known_pages` таких подряд —
   обход встал: дальше идёт то, что уже лежит в базе. Порог не «первый известный ID»,
   как в спеке: лента переставляет объявление наверх при поднятии, первое известное
   попадается на первой же странице почти всегда, и обход вставал бы, не дойдя до
   настоящего нового. Две страницы — это около 190 карточек запаса.
   Сверху есть потолок `scrape.fresh_max_pages`. Упёрлись в него — это **ошибка**
   прогона, а не успех: до известных объявлений обход не дошёл, значит часть ленты
   он не видел и нужен полный обход. Молча укоротить ленту нельзя. Но потолок,
   **названный флагом** `--max-pages`, ошибкой не считается: человек столько и
   просил, прогон встаёт с ноль ошибок и базу заливает. Отказ при этом называет
   человеку то, что человек задавал: флаг — флагом, ключ конфига — своим ключом,
   а не чужим `scrape.fresh_max_pages`, которого никто не писал.
   Режим прогона пишется в `runs.mode`: `full` (без ограничений), `partial`
   (`--max-pages`), `resume` (`--resume`), `fresh` (`--fresh`). Меркой полноты для
   следующего обхода (проверка недобора страниц из пункта 4) считается **только**
   `full` — иначе инкрементальный прогон на шести страницах стал бы нормой и
   проверка замолчала бы. Режим считается по **флагу**, а не по итоговому потолку:
   `scrape.max_pages` в конфиге — это потолок окружения, а не «человек укоротил
   обход». Иначе один ключ в конфиге молча делал бы `partial` каждый прогон,
   и тогда снятых не помечал бы никто, а мерки полноты не было бы вовсе. `--fresh` и `--resume` вместе не работают: одно идёт
   с головы ленты, другое продолжает прерванный полный обход, и командная строка
   отвечает отказом с кодом возврата 2.

6. Каждая карточка кладётся апсертом и проверяется на мусор (секция `validate`):
   сработавшие правила уходят в `listings.anomaly`, объявление сохраняется как
   есть, но в медианы не идёт и в `.xlsx` получает колонку «Сомнительно».
   Пороги из конфига накладываются на значения по умолчанию по одному:
   `validate: {price_usd: {min: 1000}}` меняет нижнюю границу и оставляет
   верхнюю на месте, а не стирает её вместе со всем правилом.
7. Точка в `price_history` ставится, только когда изменилась **сырая** цена
   (`price_raw` или `currency`), и уносит с собой курс прогона. Пересчитанные
   `price_usd`, `price_amd`, `price_per_sqm` содержательным изменением карточки
   не считаются — иначе каждое движение курса выглядело бы как смена цены у
   всей базы разом.
8. **Ушедшее с ленты помечается снятым.** После обхода активные объявления
   сверяются с тем, что встретилось на ленте; пропавшее получает `status='gone'`
   и дату в `listings.gone_at`. Помечает **только полный удачный обход**
   (`mode == "full"`, `errors == 0`): инкрементальный, укороченный и продолженный
   видели не всю ленту, и «не встретилось» у них не значит «снято».
   У пометки есть порог `scrape.max_gone_percent`: пропало больше этой доли
   активных — не помечаем ничего, считаем ошибкой прогона и пишем об этом
   в `runs.notes`. Так выглядит оборванный обход или уехавшая вёрстка, а не рынок.
   Порог выключается **`null`, а не нулём**: `max_gone_percent: 0` значит
   «пропало хоть что-то — значит сбой» и запрещает пометку, а не разрешает всё.
   Прежде ноль читался как «предохранителя нет», и оборванный обход имел право
   пометить снятой всю базу.
   Дата снятия живёт в отдельной колонке, а не выводится из `last_seen`:
   `last_seen` двигает каждый прогон, а вернувшееся объявление обязано забыть дату
   снятия. Вернулось на ленту — снова `status='active'`, `gone_at = NULL`,
   `first_seen` не трогается: это то же объявление, а не новое.
   **Возврат с того света — отдельное событие, а не обновление поля.** Апсерт
   отдаёт исход `returned`, прогон считает его счётчиком `runs.returned` и
   пишет ноту «вернулось на ленту: N», а `changes` показывает четвёртым
   разделом «Вернулись». «Объявление вернулось на рынок» — это событие рынка,
   и к обновлениям его не подмешивают. Отличить возврат от обычной встречи
   по `last_seen` нельзя — его прогон двигает всей ленте разом, — поэтому дата
   возврата лежит в своей колонке `listings.returned_at` и гаснет при следующем
   снятии: колонка отвечает на вопрос «когда это объявление вернулось», а не
   «возвращалось ли оно когда-нибудь». Считает возврат любой обход, включая
   `--fresh`: встретить снятое объявление на голове ленты он умеет не хуже
   полного, и счётчик стоит до развилки «помечать ли снятых».
   Снятое остаётся в базе и в выгрузке — цена снятой квартиры это история рынка,
   и на M2 по ней считаются медианы кластеров. В `.xlsx` статус написан
   по-русски — «на ленте» и «снято», — как и соседние «Продавец», «Новостройка»,
   «Проверено»: латинские `active` и `gone` в переведённой таблице читал
   не человек, а база.

9. **Вёрстка уехала — это видно.** Прогон считает, у какой доли карточек
   заполнено поле, и сравнивает с порогами секции `coverage`: переименованный
   класс `ge3` делает всю базу собственниками, пропавший класс района —
   базой без районов. Выход за порог — ошибка прогона с внятным текстом.
   На выборке меньше `coverage.min_sample` доля ничего не значит, и проверка
   не выносит приговора — но и не молчит: в `runs.notes` уходит строка
   «проверка вёрстки пропущена». Прогон, который вёрстку не проверял, не
   должен выглядеть как прогон, у которого всё в порядке. Пороги здесь тоже
   накладываются по одному: названный в конфиге `min_filled` не уносит
   соседний `min_share`.
10. **Ошибка отменяет заливку.** В хранилище лежит общая копия базы; прогон,
   у которого `errors > 0`, записал неполную картину, и залить её означает
   испортить ту, что была в порядке. Поэтому при любой ошибке не выполняются
   ни ротация копий, ни заливка: локальная копия остаётся на диске — посмотри
   её глазами и, если всё в порядке, `scrape --allow-upload-with-errors`.
   Заливка, срезающая число объявлений больше чем на `storage.max_shrink_percent`,
   не выполняется без `--allow-shrink`. Перед заливкой прежняя копия базы
   кладётся в хранилище под именем с отметкой времени; держим
   `storage.keep_backups` последних. Чистка считает своими только копии базы —
   те, у которых расширение базы и отметка времени, поставленная самой
   ротацией. Выгрузка `listam-20260921-0937.xlsx`, лежащая в том же хранилище,
   под чистку не попадает и места в счёте `keep_backups` не занимает.
11. **Уезжает снимок, а не файл базы.** База живёт в режиме WAL: свежие записи
   лежат в соседнем `-wal`, пока их не перенесли в основной файл. Копировать
   основной файл, пока базу держит открытой второй читатель, означает иногда
   залить копию без последнего прогона. Поэтому заливается снимок
   (`VACUUM INTO` во временный файл рядом с базой) — он целен всегда.
   Снимок не сделался — это ошибка прогона и отказ от заливки. Скачанная из
   хранилища база приходит без спутников: `-wal` и `-shm` от прежнего файла
   убираются, чтобы SQLite не принял их за свои.

`recheck` — не прогон: он не ходит на сайт и ничего не узнаёт о рынке. Он берёт
тот же замок, накатывает миграции и пересчитывает по всем строкам то, что
считается из уже записанного: пометку `anomaly` и сумму в валюте оригинала.
Цены, даты и историю он не трогает — `last_seen` не двигается, потому что
карточку никто не видел. Нужен он тогда, когда правила проверки или схема
изменились после того, как база была набрана: прогон по ленте чинит только те
карточки, что встретил сегодня, а снятая с публикации не встретится уже никогда.
Пересчитанная копия уезжает в хранилище по тем же правилам, что у прогона.

`export` ничего не мигрирует: он читает базу, а не чинит её. Схема младше той,
которую ждёт код, — внятная ошибка и код возврата 1, а не тихая правка общей
базы по дороге к таблице.

`changes` живёт по тем же правилам: он не ходит на сайт, не берёт замок и
ничего не мигрирует — только читает. Новым считается то, у чего `first_seen`
позже отметки, снятым — то, у чего позже `gone_at`, вернувшимся — то, у чего
позже `returned_at`; сменившим цену — точка в `price_history`, у которой есть
предыдущая. Первая точка объявления сменой цены не считается: это появление,
а не подешевело.

**Отметок у окна две, и это решение, а не недосмотр.** Новое и цены приносит
любой прогон, поэтому их мерка — начало последнего прогона: «что принёс
последний обход» и есть тот вопрос, ради которого команду зовут. А снятых
ставит **только полный** обход (пункт 8), и мерить их тем же началом — значит
гасить раздел «Снято» первым же часовым `--fresh`: полный обход был ночью,
пометку поставил он, а окно уехало на час назад, и в нём пусто. При расписании
из раздела «Как запускать по расписанию» человек не увидел бы снятых **никогда**.
Поэтому снятые и вернувшиеся считаются с начала последнего завершённого
**полного** обхода, и раздел называет свою мерку вслух: «снятые — с полного
обхода N (дата)». Раздел переживает часовые `--fresh` и пересобирается только
со следующим полным обходом. Полных прогонов в журнале нет — падаем на общую
мерку и тоже говорим об этом. `--hours N` задаёт **обе** отметки: человек
попросил окно в часах, и делить его надвое незачем.

**Одна карточка — одна строка.** Раздел «Цены» обходит объявления, а не точки
истории: показывается цена на начало окна и цена на конец, промежуточные точки
схлопываются. Объявление, у которого до окна точки нет, из раздела выпадает —
оно появилось внутри окна и целиком принадлежит разделу «Новые»; показывать
его ещё и в «Ценах» значило бы считать дважды. Поэтому счётчик «Сменили цену»
считает объявления и сходится с `runs.price_changed`, а не обгоняет его.

**Ноль в пороге значит «ноль», а не «выключено».** Пороги читаются одной
функцией: `null` — порога нет, число — число, в том числе 0, ключа нет —
значение по умолчанию. Прежде `int(config.get(...) or 0)` схлопывал `null`,
`0` и отсутствие ключа в один ноль, и порог, выставленный в ноль, **снимал
предохранитель** вместо того, чтобы затянуть его до упора. Читается это так:

| Порог | Что значит `0` | Что значит `null` |
| --- | --- | --- |
| `scrape.max_gone_percent` | пропало хоть что-то — сбой, не помечаем | предохранителя нет: оборванный обход пометит снятой всю базу |
| `scrape.fresh_stop_after_known_pages` | встань на первой же странице без новых | останавливаться нечему: `--fresh` дойдёт до потолка и запишется ошибкой |
| `scrape.fresh_max_pages` | потолок в ноль страниц — обход сразу упирается | потолка нет |
| `scrape.max_pages` | отклоняется на входе (страниц должна быть хотя бы одна) | полный обход до конца ленты |
| `scrape.max_pages_drop_percent` | короче прошлого удачного быть не должно вовсе | недобор страниц этим порогом не проверяется |
| `scrape.expected_pages_min` | 0 страниц хватит — проверка не срабатывает | проверки нет |

Исключение одно — `scrape.hard_page_limit`: ноль здесь по-прежнему «выключено».
Это не предохранитель данных, а защита от зацикленного пагинатора, и «потолок
в ноль страниц» не значит ничего, кроме «обхода не будет». Исключение записано
комментарием в коде и сторожевым тестом.

**Бессмысленное значение в конфиге отклоняется так же, как в командной
строке.** `--limit 0` командная строка не принимает — и `match.limit: 0`
в конфиге теперь тоже: команда встаёт кодом возврата 2 со словами «это
счётчик, и меньше единицы он ничего не показывает; чтобы снять ограничение,
ставят null». То же у `export.matches_limit` и `changes.limit`. Разница между
порогом и счётчиком здесь и проходит: у порога ноль — это самый строгий
режим и законное значение, у счётчика строк ноль не значит ничего. Так же
отклоняется и опечатка в имени веса: `match.weights` обязан называть все
шесть факторов, и `budjet: 30` вместо `budget: 30` — отказ на входе,
а не молча другой балл (прежде фактор весом 30 просто выпадал из подсчёта,
и заметить это было нечем).

**`doctor` предупреждает, но не чинит.** Проверка «Пороги прогона» печатает
все шесть значений — теми же глазами, которыми их читает прогон, — и объясняет
опасные. У проверки три состояния: `OK`, `⚠` (код возврата 0: запускать можно,
но посмотри) и `СБОЙ` (код возврата 1). `max_gone_percent: 0` — это `СБОЙ`:
снятыми не будет помечено ничего, и раздел «Снято» останется пустым навсегда.
`max_gone_percent: null`, `max_pages: N`, нулевой или пустой порог остановки
`--fresh`, отсутствие обеих проверок недобора — это `⚠`. Конфиг `doctor` не
правит ни в одном из случаев: конфиг — территория человека, дело `doctor` —
показать, чем человек рискует, пока это ещё не навредило. Отчёт, в котором
есть `⚠`, заканчивается словами «Запускать можно, но есть предупреждения»,
а не «Всё на месте»: последнее было бы неправдой.

Ошибки прогона попадают в `runs.errors` и `runs.notes`, а ненулевой счётчик
ошибок — в код возврата 1. Нулевой итог прогона никогда не даёт 0.

База открывается в режиме WAL и с `storage.busy_timeout_ms`: `export` читает
её, пока прогон пишет, а не падает с «database is locked». Схема меняется
только версионированной миграцией, и каждая накатывается одной транзакцией —
падение посреди неё не оставляет половину схемы.

## Заявки покупателей

Заявка — ядро системы: фильтр производен от неё, а не наоборот. Заявки живут
не в базе, а во внешней таблице, которую ведёт брокер; `python -m listam requests`
читает её и кладёт разобранное в базу. Источник выбирается ключом `requests.kind`
в `config/<env>.yaml`: `none` (матчинг выключен), `csv` (файл) или `gsheet`
(Google-таблица).

Строка-образец со всеми колонками — `config/requests.example.csv`. Для `csv`
скопируй его в `data/requests.csv` (папка `data/` не коммитится) и правь:

```bash
cp config/requests.example.csv data/requests.csv
.venv/Scripts/python -m listam requests
```

Чтобы перейти на Google Sheet: поставь `requests.kind: gsheet`, раскомментируй
`sheet: ${REQUESTS_SHEET}`, `credentials_file` и `range` в конфиге, положи
идентификатор таблицы в `REQUESTS_SHEET` в `.env` и расшарь таблицу на адрес
того же сервисного аккаунта, что и Google Drive (`GDRIVE_CREDENTIALS_FILE`,
отдельной переменной у таблицы нет). Разбор у обоих источников общий: `csv`
и `gsheet` обязаны давать из одной и той же строки одну и ту же заявку.

Колонок девятнадцать, порядок значения не имеет — колонки ищутся по именам
шапки:

| Колонка | Пример | Смысл |
| --- | --- | --- |
| `id` | `R-1` | идентификатор строки; по нему заявка узнаётся при перечитывании |
| `client_name` | `Ани` | имя покупателя |
| `client_phone` | `+374 00 000000` | телефон покупателя |
| `status` | `active` | `active`, `paused` или `closed`; матчатся только `active` |
| `budget_max` | `120 000 $` | потолок бюджета в USD |
| `budget_stretch` | `135000` | растянутый потолок; пусто — `budget_max` плюс `match.budget_stretch_percent` |
| `districts` | `Кентрон, Арабкир` | допустимые районы; пусто — район не ограничен |
| `districts_priority` | `Кентрон` | приоритетные районы, подмножество `districts` |
| `rooms` | `2-3` или `2,3` | допустимое число комнат |
| `area_min` | `60` | нижняя граница площади, м² |
| `area_max` | `95` | верхняя граница площади, м² |
| `floor_min` | `2` | нижняя граница этажа |
| `floor_max` | `` | верхняя граница этажа; пусто — не ограничена |
| `no_first_floor` | `да` | первый этаж клиенту не нужен |
| `no_last_floor` | `нет` | последний этаж клиенту не нужен |
| `must_have` | `ремонт` | обязательные пожелания; в M2 хранятся, но не скорятся |
| `nice_to_have` | `балкон` | желательные пожелания; там же |
| `floor_rules` | `не первый и не последний` | человеческая заметка про этажи; скорингом не читается |
| `notes` | `звонить после 18` | заметка для себя |

Форма нестрогая, смысл строгий. Пробелы, регистр и знак валюты не важны:
`1 200 $` и `1200` — одно число, `да`/`yes`/`1`/`+` — одно «да». Но
`budget_max = «примерно 100к»`, `rooms = «много»`, `area_min > area_max`,
`budget_stretch < budget_max` и неизвестный `status` — это отказ строки
целиком с текстом, называющим колонку и значение. Отклонённая строка не
роняет чтение остальных и не попадает в базу: одна опечатка в бюджете не
имеет права оставить брокера без сорока девяти других заявок, а
истолкованная наугад заявка ошибётся молча и покажет клиенту не то. Команда
в таком случае возвращает 0 с пометкой `⚠ Не разобрано: N`, а `doctor`
показывает источник и число заявок отдельной строкой.

Запятая внутри значения обязана стоять в кавычках:
`"семья с ребёнком, смотрит с октября"`. Без кавычек значений в строке
становится больше, чем колонок в шапке: заметка обрезается первой же запятой,
а всё, что за ней, съезжает на колонку. Такая строка отклоняется целиком —
«значений больше, чем колонок в шапке», с названным лишним куском, — и
остальные заявки читаются как обычно.

**Строка исчезла из таблицы — заявка закрывается.** Источник — договор
двусторонний: брокер удалил строку, и `python -m listam requests` ставит
заявке `status: closed`, называя её в отчёте («закрыты (нет в источнике):
R-3»). Иначе ушедший месяц назад клиент продолжал бы матчиться, лезть
в витрину и в выгрузку. Матчи закрытой заявки остаются в базе — на них след
звонка, — но подбор её больше не берёт, и в витрине её раздела нет.
Одно исключение: **пустой источник ничего не закрывает**. Таблица, не
отдавшая ни одной строки, — это почти всегда сбой доступа, а не «все клиенты
ушли», и терять из-за него работу месяца нельзя; команда говорит об этом
отдельной строкой.

## Матчинг и витрина

```bash
.venv/Scripts/python -m listam cluster             # кластеры-дубли по всей базе
.venv/Scripts/python -m listam match --all         # подобрать по всем активным заявкам
.venv/Scripts/python -m listam match --new         # только по объявлениям последнего прогона
.venv/Scripts/python -m listam match --request R-1 # по одной заявке
.venv/Scripts/python -m listam matches             # витрина: что подобралось
```

**Кластер — это одна квартира, выставленная несколько раз.** На боевых числах
(срез ленты за 21.09.2026) 20 595 объявлений сворачиваются в 14 355 кластеров,
из них 2 824 многочленных — дедуп убирает больше шести тысяч лишних звонков,
а крупнейший кластер собрал одну и ту же квартиру из 36 карточек. До
QA-ужесточения кластеров было 14 232: ширина кластера тогда ничем не
ограничивалась, и цепочка «60 → 62 → 64 → 66 м²» при допуске 2 м² склеивалась
в один кластер шириной 6 м². Теперь состав, вышедший за допуск, разводится
по разным кластерам — отсюда 123 кластера разницы на одних и тех же
объявлениях. Ключ кластера: район, нормализованная улица (`ул.`, `улица`,
`փող.` отбрасываются), комнаты, этаж, этажность и площадь с допуском
`match.cluster.area_tolerance` (2 м²: обмеры одной квартиры у разных агентств
расходятся). Объявление без улицы, без района или без площади образует
кластер из самого себя — улицы нет у каждого пятого объявления, и без неё
ключ склеил бы разные квартиры одного дома, спрятав от клиента настоящий
вариант. Матч пишется на самое дешёвое объявление кластера, остальные его
члены матчей не порождают; в витрине кластер помечен: «3 объявления,
разброс $11 000».

**Балл — это доля от того, что вообще можно было набрать.** Сначала жёсткие
критерии: район не из заявки, комнат меньше минимума, цена выше растянутого
бюджета, площадь ниже `area_min` — такое объявление в матчи не попадает
вовсе, как и снятое с ленты или помеченное аномалией. Прошедшее оценивается
шестью факторами с весами из секции `match.weights`:

| Фактор | Вес | За что |
| --- | --- | --- |
| `budget` | 30 | попадание в бюджет; за растяжку балл ниже |
| `district` | 20 | приоритетный район выше просто допустимого |
| `price_per_sqm` | 20 | выгодность против медианы района, а не кластера |
| `area_rooms` | 15 | площадь и число комнат внутри запрошенного |
| `floor` | 10 | этаж в диапазоне, не первый и не последний, если клиент против |
| `seller_type` | 5 | собственник выше агентства |

Фактор, для которого не хватает данных **у заявки или у объявления**, из
знаменателя исключается: заявка, промолчавшая про этажи, не получает десять
баллов ни за что, а заявка без диапазона площади их не теряет. Идеальное
попадание — 100 в обоих случаях.

**`--new` — это «что тронулось», а не «что появилось».** Ночной сценарий
`scrape && match --new` мерит выборку не датой появления объявления, а
началом прошлого прогона: в неё попадает появившееся, вернувшееся на ленту
и **сменившее цену**. Квартира, которая вчера стоила 130 000 $, а сегодня
118 000 $ и наконец влезла в бюджет, новой не стала — но звонить по ней надо
сегодня, и прежняя мерка по `first_seen` теряла именно её, то есть главное
событие рынка. Отдельно от объявлений мерятся заявки: заявку, которую
правили после её последнего подбора (`requests.matched_at`), `--new` гонит
по **всей** базе, а не по выборке прогона, — выросший на десять тысяч бюджет
должен увидеть то, что подходит ему уже сейчас, а не ждать ночного `--all`.

**Пороги — это два разговора, а не один.** `match.thresholds.hot: 70` — «звони
сейчас»: такой вариант уйдёт в немедленное уведомление на M3.
`match.thresholds.digest: 40` — «покажи вечером»: ниже этого балла вариант
в витрину не попадает вовсе. `matches` показывает от дайджестного порога и
не больше `match.limit` строк; оба числа переопределяются флагами
`--min-score` и `--limit`, и оба живут в конфиге, а не в коде.

Лист «Матчи» в `.xlsx` тоже с потолком: `export.matches_limit: 200` — столько
лучших строк на заявку уходит в выгрузку. Без потолка боевая база давала
десятки тысяч строк на одном листе. Ноль и отрицательное здесь — отказ кодом
возврата 2 (это счётчик строк, а не порог), а `null` значит «без потолка».

**У матча есть конец жизни, и это не удаление строки.** Квартира подорожала
со 120 000 до 400 000 $ — полный проход (`match --all`, но не `--new`) её
больше не подтверждает, и матч **закрывается**: в строку пишутся `retired_at`
и `retired_reason`, витрина и лист «Матчи» её больше не показывают, а отчёт
прогона говорит «Закрыто матчей: N — вариант больше не подходит». Строка при
этом остаётся в базе: на ней след звонка (`status`, `reject_reason`), и «мы
звонили по этой квартире» не должно исчезать вместе с подорожавшим
объявлением. Подтвердившийся снова матч воскресает — `retired_at` гасится,
`first_matched_at` остаётся прежним. Закрывается матч и тогда, когда в
кластере появился вариант дешевле: представителем становится он, а строка
на прежнего представителя закрывается, — иначе клиент получал бы две карточки
одной квартиры. Закрывает матчи только полный проход: `--new` смотрит на
часть базы и о неподтверждённом остальном ничего не знает.

Матч на снятое объявление из витрины **не исчезает, а помечается**: минусом
и словами «снято с ленты» в `matches`, колонкой «Статус объявления» на листе
«Матчи» в `.xlsx`. Снятое с ленты матч не закрывает: проход его не видел
вовсе, а это не то же самое, что «видел и не подтвердил». «Мы звонили по этой квартире» должно переживать уход
объявления с ленты. По той же причине пересчёт не трогает след звонка:
`status` матча (`новый`, `отправлен`, `звонили`, `отказ`) и причину отказа
пишет человек, а ночной `match --all` обновляет только балл, его разбор и
снимок кластера. Смена номера прогона сама по себе обновлением не считается:
между любыми двумя пересчётами он меняется всегда, и иначе первый же ночной
`scrape && match --all` объявлял бы обновлёнными все матчи разом. У матча
номер прогона значит «в каком прогоне он в последний раз менялся».

`python -m listam export` кладёт витрину на отдельный лист «Матчи» рядом
с листом объявлений — по тем же правилам: шапка заморожена, автофильтр,
числа числами, ссылка кликабельна.

## Уведомления и дайджест

```bash
.venv/Scripts/python -m listam matches --new       # что нового со вчера, в терминал
.venv/Scripts/python -m listam notify --hot        # «звони сейчас», раз в час
.venv/Scripts/python -m listam notify --digest     # дневная сводка, вечером
.venv/Scripts/python -m listam notify --feed       # что пришло на ленту вне заявок
.venv/Scripts/python -m listam notify --digest --dry-run   # показать и не посылать
```

**Событие — это не «матч есть», а «сегодня с ним что-то случилось».** На боевых
числах порог `hot: 70` даёт 35 572 горячих матча, а одна широкая заявка — 7 515:
посылать по одному сообщению на матч нельзя ни в каком виде. Уведомление
показывает четыре вида событий: вариант **появился**, **подешевел**, **вернулся**
(закрытый матч снова подтвердился) и **отпал**. Последнее живёт отдельной тихой
строкой внизу дайджеста: закрытие не повод звонить, это объяснение, куда делась
вчерашняя карточка.

**Окно считается от прошлой отправки, а не «за сутки».** Каждая успешная
отправка пишет строку в журнал `notifications`; следующая начинается там, где
кончилась прошлая. Поэтому повторный запуск не шлёт то же самое второй раз,
а отказ канала ничего не теряет: строки нет — окно не сдвинулось. Отправок ещё
не было — берётся `notify.<вид>.fallback_hours`, и команда говорит об этом
вслух.

**Заявка, у которой событий сотни, помечается.** На заявку печатается
`notify.<вид>.per_request` лучших по баллу и честный хвост «…и ещё N из M».
Перевалившая за `notify.digest.wide_request` получает отдельную строку: столько
событий в сутки — это незаполненная заявка, а не рынок.

**`--dry-run` показывает то, что ушло бы в чат, и не пишет в журнал.**
Отправленное не отзывается, и брокер не должен узнавать об ошибке из чата
клиента. Тот же текст можно посмотреть витриной: `matches --new`.

**Окно у витрины и у сообщения одно, а потолок — разный.** `matches --new`
и `notify --digest` спрашивают базу об одном и том же и берут отметку из одного
журнала; иначе сличить отправляемое глазами было бы нельзя. А вот строк на
заявку витрина показывает `match.limit` (50), сообщение — `notify.<вид>.per_request`
(5 и 10): у терминала есть полоса прокрутки, а у сообщения в чате её нет.

**Канал Telegram — `notify.kind: telegram`.** Токен бота и чат живут в `.env`
(`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`), в конфиге — только ссылки
`${TELEGRAM_BOT_TOKEN}` и `${TELEGRAM_CHAT_ID}`. Пустой секрет — отказ кодом 2
до работы; `doctor` показывает канал строкой «Уведомления». Telegram не берёт
больше 4 096 символов, поэтому **каждая заявка уходит отдельным сообщением**:
брокер пересылает раздел клиенту, и чужой клиент в пересланном недопустим.
Раздел длиннее предела режется между строками, ссылка не рвётся никогда. Сколько
заявок с событиями — столько сообщений; если их десятки, заявки широки, и лечит
это заявка, а не канал. Отказ на середине команда называет («доставлено 3
из 7»): журнал не пишется, и следующий запуск пошлёт всё заново, включая дошедшее.

Живая проверка канала — `tests/live`, только явно:
`TELEGRAM_LIVE=1 .venv/Scripts/python -m pytest -q tests/live -s`. Она шлёт
настоящие сообщения в `TELEGRAM_CHAT_ID` и читает их в Telegram Web через
Playwright (`requirements-dev.txt`); вход в Telegram Web делается один раз руками
в профиль `tmp/telegram-profile`. В обычной батарее эти тесты пропускаются.

## Как запускать по расписанию

Планировщик живёт в системе, а не в инструменте: своего демона у `listam` нет
и не будет. Расписание двухслойное.

* **Инкрементальный обход — раз в час.** `scrape --fresh && match --new`
  проходит единицы страниц, приносит то, что появилось за час, и сразу
  примеряет новое к заявкам. Это дежурный режим.
* **Полный обход — раз в сутки.** `scrape && match --all`. Только полный обход
  проверяет ленту целиком и потому только он имеет право помечать снятые
  (пункт 8) и быть меркой полноты для проверки недобора страниц (пункты 4
  и 5). Час-полтора в сутки — его цена; ночной `match --all` за ним
  пересчитывает баллы по всей базе, не трогая след звонка.

Подбор вынесен в отдельную команду намеренно: краулер на 864 строки — не место
для движка скоринга, а `scrape && match` даёт ровно то же поведение и
проверяется по частям. Замок у обеих команд общий, так что `match` не
начнётся посреди чужого обхода — он честно скажет, что прогон уже идёт.

Это расписание — то самое, на котором `changes` раньше терял раздел «Снято»:
пометку ставит только ночной полный обход, а окно дельты уезжало к началу
последнего часового `--fresh`, и снятых человек не видел никогда. Теперь у
снятых и вернувшихся своя мерка — последний полный обход (см. `changes` выше), —
и раздел переживает часовые прогоны до следующей ночи.

Накладываться они не могут: замок прогона (пункт 3) не пускает второй `scrape`,
пока идёт первый. Если часовой запуск пришёлся на середину суточного, он честно
скажет, что прогон уже идёт, и уйдёт ни с чем — это нормально, следующий придёт
через час.

Windows, `schtasks` (обход идёт через браузер с окном, поэтому задача ставится
на вход пользователя, а не на `SYSTEM`):

```bat
schtasks /create /tn "listam-fresh" /sc hourly /ru "%USERNAME%" /it ^
  /tr "cmd /c C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam scrape --fresh && C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam match --new"
schtasks /create /tn "listam-full" /sc daily /st 04:00 /ru "%USERNAME%" /it ^
  /tr "cmd /c C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam scrape && C:\Users\Admin\Downloads\list\.venv\Scripts\python.exe -m listam match --all"
```

Сервер без экрана, `cron` — браузер заворачивается в виртуальный экран
(`headless: false` трогать нельзя, см. «Как обходится Cloudflare»):

```cron
0 * * * *  cd /srv/listam && xvfb-run -a .venv/bin/python -m listam scrape --fresh && .venv/bin/python -m listam match --new
0 4 * * *  cd /srv/listam && xvfb-run -a .venv/bin/python -m listam scrape && .venv/bin/python -m listam match --all
```

Ненулевой код возврата — повод посмотреть `runs.notes` за этот прогон:
там лежит и причина остановки, и отказ от пометки снятых, и отказ от заливки.

## Устройство

```
listam/
  ports/        интерфейсы: Storage, Database, Fetcher, RateProvider, Exporter,
                RequestsSource, Notifier
  adapters/     реализации: local/gdrive, sqlite, playwright/http/files,
                rate_am/fixed, xlsx_local
  domain/       модель данных, разбор цен, проверки и доли заполненности
  migrations/   версионированные миграции схемы
  runner.py     общий каркас команд, пишущих в базу: замок, свежая копия,
                миграции, снимок и заливка — один порядок на всех
  wiring.py     единственное место, где код знает имена адаптеров
  doctor.py     самопроверка окружения
  cli.py        командная строка
config/         dev.yaml, prod.yaml — без секретов
tests/          контрактные тесты на каждый порт + тесты домена
```

**Команды, пишущие в базу, мигрируют базу сами.** `cluster`, `requests`,
`match`, `notify` и `recheck` стоят на общем каркасе (`listam/runner.py`): он
берёт замок, забирает свежую копию из хранилища и **накатывает миграции** —
отказа «схема старая» у них нет. Прогон `scrape` делает то же своим путём.
Мигрирует даже `notify --dry-run`: пробный прогон не шлёт и не пишет журнал,
но рабочую копию переводит на новую схему. Отказывают те, кто базу только
читает: `export`, `changes`, витрина `matches` и проверка `doctor`. Поэтому
`doctor` на старой базе говорит «запускать рано» строже, чем ведут себя
команды, а совет «накати миграции: `python -m listam recheck`» верен, но не
единственный путь — мигрирует любая пишущая команда.

Правило, которое держит переносимость: ни один аккаунт, путь, ключ и идентификатор
файла не зашит в код. Всё внешнее — за портом, выбор реализации — в конфиге,
секреты — только в `.env`.

## Переезд на другой аккаунт или хранилище

1. Скопировать `data/listam.sqlite` в новое хранилище — база это один файл.
2. Заполнить `.env` новыми идентификаторами (образец — `.env.example`).
3. Переключить `storage.kind` в нужном `config/<env>.yaml`.
4. `APP_ENV=prod python -m listam doctor` — отчёт должен быть без строк «СБОЙ».

Для Google Drive дополнительно: `pip install -r requirements-gdrive.txt`, сервисный
аккаунт с ключом в JSON, папка Drive расшарена на адрес сервисного аккаунта с правом
редактирования. `GDRIVE_FOLDER` — идентификатор папки, `GDRIVE_CREDENTIALS_FILE` —
путь к ключу.

## Как обходится Cloudflare

Перед list.am стоит проверка Cloudflare: на обычный HTTP-запрос сайт отвечает
`403` с заголовком `Cf-Mitigated: challenge`. Поэтому страницы берёт настоящий
браузер — адаптер `playwright` порта `Fetcher` (`scrape.kind: playwright`).

Что выяснилось на живом сайте 21.09.2026:

| Как ходим | Что отдаёт list.am |
| --- | --- |
| `requests` | 403, проверка Cloudflare |
| Playwright, headless | 403 — headless отличают и режут |
| Playwright, headed, без флага ниже | первая страница 200, вторая и дальше 403 |
| Playwright, headed, с флагом | 200 на все страницы подряд |

Отсюда две настройки, которые нельзя трогать не подумав:

* `headless: false` — браузер запускается с окном. На сервере без экрана его
  заворачивают в виртуальный: `xvfb-run -a python -m listam doctor`.
* флаг `--disable-blink-features=AutomationControlled` — без него Chromium
  сообщает странице, что им управляет автоматика. Флаг в коде адаптера, не в
  конфиге: это не вкус, а условие работы.

`profile_dir` (по умолчанию `./data/browser`) держит профиль браузера между
запусками, чтобы не проходить проверку каждый раз заново. Профиль иногда
протухает — сохранённое состояние перестаёт годиться, и проверка начинает
приходить на каждую страницу. Адаптер это распознаёт и один раз за прогон
сносит профиль, начиная с чистого листа; в логе это видно как успешный
повтор после сбоя.

Сносит он при этом только свой каталог — тот, который сам завёл и пометил
изнутри. И `profile_dir`, накрывающий рабочую папку (`storage.work_dir`,
`storage.directory`, `scrape.pages_dir`, `export.path`), прогон не запускает
вовсе: опечатка `profile_dir: ./data` иначе унесла бы базу. `storage.directory`
в этом списке не зря: при `storage.kind: local` это и есть хранилище — общая
копия базы и все её бэкапы.

Если проверка не проходит и с браузером, помогает другой адрес: армянский
домашний интернет или VPS. Cloudflare включает проверку в том числе по
репутации IP.

### Когда сайта под рукой нет

У порта `Fetcher` есть реализация `files`: она читает страницы с диска тем же
кодом, каким читала бы ленту. Нужна, чтобы переразобрать старый снимок после
правки парсера, не трогая сайт, — и чтобы работать с сохранённой вручную
страницей. Переключается `scrape.kind: files`, страницы лежат в
`data/pages/`, имя файла получается из пути URL: `/category/60/2` →
`category-60-2.html`. Подробности — в `docs/сохранённые-страницы.md`.

## Тесты

```bash
.venv/Scripts/python -m pytest -q
```

Контрактные тесты (`tests/contracts/`) написаны против портов: подменили
реализацию — тест обязан пройти без изменений. Батарея порта `Fetcher` гоняется
на всех трёх реализациях, включая `playwright` — он ходит в локальный тестовый
сервер, а не на list.am. Тесты gdrive пропускаются, пока не заданы
`GDRIVE_FOLDER` и `GDRIVE_CREDENTIALS_FILE`; тесты playwright — пока не
установлен пакет.
