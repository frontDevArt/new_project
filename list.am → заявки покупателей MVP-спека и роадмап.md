# list.am → заявки покупателей: MVP-спека и роадмап

2026-09-21 · @Someone

## Бизнес-модель: что строим

Это инструмент брокера, работающего от покупателя, а не поиск квартиры для себя. Покупатель оставляет заявку и сам по 20 000 объявлений не лазит — в этом и есть услуга.

Процесс:

1. Клиент оставляет заявку: бюджет, район, комнаты, площадь, пожелания.
2. Сегодня под эту заявку на рынке ничего нет.
3. Завтра появляется подходящее объявление — узнать об этом надо первым.
4. Бот сообщает о совпадении → звоним продавцу → звоним клиенту → показ.

Из этого следуют три решения, определяющие всю архитектуру.

**Ядро системы — заявка, а не фильтр.** Заявка это долгоживущая сущность со статусом, историей показов и обратной связью клиента («район не тот», «первый этаж не смотрим»). Фильтр — производная от заявки.

**Матчинг двусторонний.** Нужны оба направления: новое объявление → все активные заявки (ежечасный прогон) и новая заявка → вся накопленная база (в момент создания заявки). Второе даёт ценность с первого дня: клиент оставляет заявку, а у нас уже лежит 20 000 объявлений, среди которых может быть его вариант.

**Скорость — и есть конкурентное преимущество.** Выигрывает тот, кто позвонил первым. Час задержки на хорошем варианте в Центре — проигранная сделка. Отсюда требование к циклу мониторинга: дёшево, часто, инкрементально.

Побочный эффект, который со временем станет основным: накопленная база сама по себе актив. Через три месяца у нас история цен, медиана $/м² по районам и понимание, кто из агентств чем торгует. Этим аргументируется цена перед клиентом.

Аренда в MVP не входит. Схема данных проектируется так, чтобы она добавлялась позже сменой парсера, без переделки ядра.

## Что проверено на list.am

Разведка проведена 21.09.2026 по категории [Բնակարանների վաճառք (продажа квартир), category/60](https://www.list.am/category/60) — 20 607 объявлений на момент проверки.

| Что | Результат | Следствие для нас |
| --- | --- | --- |
| Рендер страницы категории | Серверный, читается обычным HTTP-запросом | Браузер для сбора списка не нужен |
| Пагинация | По пути: `/category/60/2`, `/3`, … | Простой обход, без query-параметров |
| Поля в карточке списка | Цена, заголовок, комнаты, площадь, этаж/этажность, район, тип продавца, «новостройка», статус проверки | Открывать каждое объявление ради базовых полей не нужно — экономия \~95% запросов |
| Идентификатор | В ссылке: `/item/24254997` | Готовый первичный ключ для дедупа |
| Сортировка | Есть «по дате» | Основа инкрементального прогона |
| Язык | Есть `/ru/category/60` | Парсим русскую версию, поля сразу по-русски |
| Телефон продавца | Только после клика по кнопке звонка, в модалке | Единственное дорогое поле; нужен браузер |
| Тип продавца | «Սեփականատիրոջից» (от собственника) / «Գործակալություն» (агентство) | Прямой признак ценности лида |

Отдельно: в выдаче видны **массовые дубли** — одна квартира публикуется несколькими агентствами с разными ID и разбросом цены. Например, по Аджапняку идёт серия почти идентичных объявлений с одного адреса. Это не шум, а отдельная задача (см. раздел про дедуп).

Источники: [category/60](https://www.list.am/category/60), [robots.txt](https://www.list.am/robots.txt).

## Ограничения и правила игры

В `robots.txt` list.am есть два запрета, которые прямо касаются проекта:

- Краулеры Anthropic (`ClaudeBot`, `anthropic-ai`, `Claude-Web`) запрещены целиком.
- Для всех ботов запрещены category-URL с параметрами: `n=`, `crc=`, `price1=`, `price2=`, `rooms=`, `srt=`, `type=`, `cmtype=`. То есть именно те ссылки, которые получаются при накликивании фильтров в интерфейсе.

Из этого — четыре правила, которые заложены в архитектуру ниже.

**Фильтруем у себя, а не запросом.** Тянем общую ленту, отсортированную по дате, по путевой пагинации, и всю фильтрацию делаем локально. Это и соответствует их правилам, и на порядок гибче: фильтры перестают зависеть от того, что list.am разрешил в URL.

**Частота — компромисс между скоростью и вежливостью.** Инкрементальный прогон раз в 30–60 минут это 1–2 запроса за раз, незаметная нагрузка. Опрос раз в 5 минут — это уже поведение, на которое Cloudflare отвечает баном IP. Стартуем с часа, при необходимости ужимаем до 30 минут.

**Телефоны собираем только под конкретный матч.** Никакой массовой выгрузки контактов «про запас». Телефон добирается лениво: объявление совпало с реальной заявкой живого клиента → достаём номер → звоним по поводу именно этого объявления. Это и технически дешевле, и единственная защищаемая позиция, если возникнут вопросы.

**Персональные данные клиентов — отдельный контур.** В базе лежат имена и телефоны покупателей. База не должна уезжать в публичные шары и в артефакты с открытой ссылкой.

Есть и более прочный путь, который стоит держать в голове на горизонте: у list.am есть собственная функция сохранённого поиска с уведомлениями. Если проект перерастёт в коммерческий сервис, разговор с ними об официальном доступе или партнёрстве снимает всю эту категорию рисков разом. Для MVP в текущем объёме — личный инструмент брокера, низкая частота, без перепродажи данных — рамки выше достаточны.

## Архитектура и модель данных

База — SQLite. Excel остаётся, но как витрина, а не как хранилище.

Причина: нужна история цен (падение с $145k до $132k — главный сигнал в этом бизнесе), нужны статусы (объявление исчезло = продано или снято), нужен нечёткий дедуп, нужны индексы по 20 000+ строк и связка «заявка ↔ объявление ↔ звонок». В Excel это разваливается на второй неделе. SQLite внизу + генерация свежего `.xlsx` или Google Sheet после каждого прогона даёт оба мира.

### Таблицы

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `listings` | Текущее состояние объявления | `id` (PK, из URL), `url`, `first_seen`, `last_seen`, `status` (active/gone), `title`, `district`, `street`, `price_usd`, `price_amd`, `area`, `rooms`, `floor`, `floors_total`, `price_per_sqm`, `seller_type`, `verified`, `new_build`, `cluster_id` |
| `price_history` | Динамика цены | `listing_id`, `seen_at`, `price_usd` |
| `requests` | Заявки покупателей — ядро системы | `id`, `client_name`, `client_phone`, `created_at`, `status` (active/paused/closed), `budget_max`, `budget_stretch`, `districts[]`, `rooms[]`, `area_min`, `area_max`, `floor_rules`, `must_have`, `nice_to_have`, `notes` |
| `matches` | Связка заявки и объявления | `request_id`, `listing_id`, `score`, `matched_at`, `status` (new/sent/called/rejected), `reject_reason` |
| `contacts` | Телефоны продавцов, заполняются лениво | `listing_id`, `seller_name`, `phone`, `fetched_at` |
| `runs` | Журнал прогонов | `started_at`, `pages_fetched`, `new_listings`, `new_matches`, `errors` |

`price_per_sqm` считаем сами — на сайте его в карточке нет, а это основной инструмент оценки.

Таблица `matches` с полем `reject_reason` — не бюрократия. Когда клиент говорит «нет, первый этаж не смотрим», это должно вернуться в заявку и сузить будущие матчи. Без этого система будет предлагать одно и то же.

### Где живёт база между запусками

Проблема: задача по расписанию стартует в облаке с чистого листа, локальный файл ей недоступен. Варианты:

| Вариант | Плюс | Минус |
| --- | --- | --- |
| SQLite на твоём компьютере | Быстро, все данные под рукой | Задача требует, чтобы компьютер был включён и подключён |
| SQLite в Google Drive, качаем и заливаем каждый прогон | Работает без твоего компьютера, круглосуточно | Медленнее, риск конфликта при параллельных запусках |
| Внешний хостинг (VPS, Railway, Fly) | Полный контроль, настоящий cron | Нужен деплой и оплата |

Решено на сейчас: Google Drive — но через адаптер, так что это настройка, а не архитектура (см. следующий раздел). Круглосуточная работа важнее скорости, а объём данных мал. Там же, в Drive, лежит Google Sheet с заявками, который ты заполняешь вручную и который скрипт читает перед каждым матчингом. Порядок прогона: скачать базу → собрать новое → прочитать заявки → посчитать матчи → залить базу и выгрузку обратно.

## Переносимость: сегодня тест, завтра рабочий аккаунт

Правило, которое действует с первой строки кода: **ни один аккаунт, путь, ключ, идентификатор файла и внешний сервис не зашит в код**. Всё внешнее живёт за адаптером, а какой адаптер использовать — решает конфиг.

Сейчас мы на тестовом аккаунте и на Google Drive. Завтра это может быть рабочий Google-аккаунт, локальная папка, OneDrive с Excel или сервер с Postgres. Переезд должен стоить правки одного файла конфигурации, а не переписывания проекта.

### Порты и их реализации

| Порт (интерфейс) | Что делает | Реализации сейчас | Что добавится потом |
| --- | --- | --- | --- |
| `Storage` | Хранит файл базы между прогонами | `local`, `gdrive` | `s3`, `onedrive` |
| `Database` | Читает и пишет объявления, заявки, матчи | `sqlite` | `postgres` |
| `RequestsSource` | Отдаёт список активных заявок | `gsheet`, `csv` | `xlsx`, `db`, веб-форма |
| `Exporter` | Отдаёт витрину для человека | `xlsx_local`, `gdrive_upload` | `gsheet_write` |
| `RateProvider` | Курс AMD→USD | `rate_am`, `fixed` | ЦБ Армении |
| `Notifier` | Доставляет алерты | `none`, `stdout` | `telegram`, `email` |
| `Fetcher` | Тянет страницы list.am | `http` | `browser` (для телефонов на M4) |

Каждый порт — маленький абстрактный класс на 3-5 методов. Для каждого один и тот же контрактный тест: подменили реализацию, тест обязан пройти без изменений.

### Конфигурация

Два файла, оба вне кода:

```yaml
# config/dev.yaml — не секретный, лежит в репозитории
env: dev
storage:
  kind: gdrive
  folder: ${GDRIVE_FOLDER}      # подставляется из окружения
  db_filename: listam.sqlite
requests:
  kind: gsheet
  sheet: ${REQUESTS_SHEET}
export:
  kind: xlsx_local
  path: ./out
rate:
  kind: rate_am
notify:
  kind: stdout
scrape:
  base_url: https://www.list.am/ru
  category: 60
  delay_seconds: 1.5
  max_pages: 20                 # в prod — null, то есть до конца
```

Секреты (токены, идентификаторы папок и таблиц, ключи сервисного аккаунта) — только в `.env`, который никогда не попадает в репозиторий. В репозитории лежит `.env.example` со списком нужных переменных и пустыми значениями.

Переключение окружения — одной переменной: `APP_ENV=prod`. Никаких закомментированных блоков «раскомментировать для продакшена».

### Переезд на рабочий аккаунт

1. Скопировать файл `listam.sqlite` в новое хранилище — база это один файл, она ни к чему не привязана.
2. Создать `config/prod.yaml` и заполнить `.env` новыми идентификаторами.
3. Запустить `python -m listam doctor` — команда проверяет доступ к хранилищу, чтение заявок, получение курса, права на запись, и печатает отчёт.
4. Прогнать один цикл с `--dry-run`, убедиться, что ничего не пишется лишнего.

### Что легко нарушить и чего делаем нельзя

Идентификатор файла или папки Google Drive внутри кода или внутри данных — только в конфиге. Абсолютные пути вида `/Users/artur/...` — только относительные от корня проекта. Локальное время — все отметки времени в UTC, в человеческий вид переводим только на выгрузке. Схема базы меняется только версионированными миграциями, чтобы обновление не потребовало собирать 20 000 объявлений заново.

## Движок матчинга

Матч — не булево значение, а оценка от 0 до 100. Вариант на $5 000 дороже бюджета всё равно стоит звонка, а система с жёсткими порогами его выбросит и клиент об этом никогда не узнает.

```mermaid
flowchart LR
  A[Новое объявление] --> B{Жёсткие<br/>критерии}
  B -- не прошло --> X[Отбой]
  B -- прошло --> C[Скоринг]
  C --> D{Дубль?}
  D -- да --> E[Дешёвший в кластере]
  D -- нет --> F[Запись в matches]
  E --> F
  F --> G{score >= 70?}
  G -- да --> H[Бот: звони сейчас]
  G -- нет --> I[Дайджест раз в день]
```

### Жёсткие критерии (отсекают сразу)

Район не из списка заявки; комнат меньше минимума; цена выше растянутого бюджета (`budget_stretch`, обычно +10% к `budget_max`); площадь ниже минимума. Всё остальное — мягкое.

### Скоринг

| Фактор | Вес | Логика |
| --- | --- | --- |
| Попадание в бюджет | 30 | В `budget_max` — полный балл; между `budget_max` и `budget_stretch` — убывает линейно |
| Район | 20 | Приоритетный район заявки выше, чем просто допустимый |
| Цена за м² против медианы кластера | 20 | Ниже медианы — выше балл; это и есть «выгодность» |
| Площадь и комнаты | 15 | Попадание в диапазон |
| Этаж | 10 | Штраф за первый и последний, если клиент их не хочет |
| Тип продавца | 5 | Собственник выше агентства: нет дележа комиссии и торг прямее |

Пороги: `score >= 70` — немедленное уведомление в бот; `40–69` — дневной дайджест; ниже — только в базе.

### Дедуп кластеров

Одна квартира висит у нескольких агентств с разными ID и разбросом цены. Клиенту нельзя звонить дважды про одну и ту же квартиру — это выглядит как непрофессионализм.

Нечёткий ключ кластера: `район + улица + площадь ±2 м² + этаж/этажность + комнаты`. Внутри кластера показываем вариант с минимальной ценой и помечаем «N объявлений, разброс $X». Кластер, а не объявление, является единицей матчинга.

### Оба направления

**Новое объявление → активные заявки.** Ежечасный прогон: тянем ленту по дате до первого уже известного ID и останавливаемся. Обычно 1–2 страницы вместо двухсот.

**Новая заявка → вся база.** В момент создания заявки прогоняем её по всем активным объявлениям. Это даёт результат в первый же день работы с клиентом, ещё до того, как появится хоть одно новое объявление.

## Роадмап

Каждый этап — отдельная сессия и рабочий результат на руках, а не полуфабрикат.

| Этап | Что делаем | Готово, когда |
| --- | --- | --- |
| **M0. Парсер и снимок** | Парсер карточек с `/ru/category/60`, схема SQLite, обход N страниц, выгрузка в `.xlsx` | На руках база на 1 000–2 000 объявлений и таблица, которую можно открыть и отсортировать |
| **M1. Дельта и история** | Инкрементальный прогон до известного ID, `price_history`, пометка `status=gone`, журнал прогонов | Повторный запуск добавляет только новое и фиксирует изменения цен |
| **M2. Заявки и матчинг** | Таблица `requests`, движок скоринга, дедуп кластеров, `matches`, прогон в обе стороны, чтение заявок из Google Sheet | Заводим реальную заявку и получаем ранжированный список вариантов из базы |
| **M3. Уведомления** | Telegram-бот, немедленные алерты при `score >= 70`, дневной дайджест | Новое подходящее объявление приходит в телефон без ручного запуска |
| **M4. Телефоны по требованию** | Добор контакта через браузер по конкретному матчу, запись в `contacts` | Из уведомления можно сразу получить номер продавца |
| **M5. Интерфейс** | Дашборд: ввод заявок, список матчей, статусы звонков, аналитика $/м² по районам | Работа идёт из интерфейса, Excel нужен только для выгрузки клиенту |
|  |  |  |
|  |  |  |

После M5 — расширение на другие категории: дома (`/1386`), коммерция (`/199`), аренда (`/56`). Меняется только парсер карточки, ядро остаётся.

Первые три этапа — это уже работающий инструмент. M0 и M1 реально уложить в одну сессию. Пятьдесят заявок в работе означают, что вручную сверять матчи не выйдет: ввод заявок таблицей и автоматический скоринг нужны с самого начала M2.

## Принятые решения

Закрыто 21.09.2026. Всего, что ниже, достаточно для старта M0.

- [x] **Где живёт база между прогонами** — Google Drive. Скрипт скачивает базу перед прогоном и заливает обратно после
- [x] **Объём стартового снимка** — только Ереван или вся Армения; решено тянуть всю категорию целиком — 20 607 объявлений, около 200 страниц, порядка 7 минут с паузами. Ереван отфильтруем локально, это бесплатно. В M0 сначала 20 страниц на проверку парсера, потом полный обход
- [x] **Валюта хранения** — приводим всё к USD (на сайте цены и в долларах, и в драмах). Курс берём с rate.am и записываем в журнал прогона, чтобы старые цифры оставались воспроизводимыми
- [x] **Канал уведомлений** — Telegram-бот требует токена от @BotFather. Заводим на этапе M3, до тех пор уведомлений нет
- [x] **Откуда берутся заявки** — ты вводишь вручную в Google Sheet, лежащий в том же Drive; скрипт читает его каждый прогон
