# M3.5. Боевой запуск: дизайн

2026-09-23 · подготовлено перед планом реализации

Промежуточный этап между M3 и следующими за ним. Источник —
`docs/анализ-после-M3.md`: разделы «Где разошлись с целью», «Решение лучше
исходного: двухступенчатая воронка», «Что входит в M3.5», пункт 8 (вёрстка
Telegram) и таблица долгов. Смысл этапа — не новая возможность, а то, чтобы
система **каждый день работала на брокера сама**.

**Готово, когда:** неделю система сама обходит ленту и шлёт уведомления без
ручного запуска, «звони сейчас» по живой заявке приносит единицы вариантов,
а не сотни, и из сообщения за секунду понятно, кому звонить и про какую
квартиру.

Это главный критерий. Шлифовка краевых случаев, которых живой брокер не
заметит, — не в этом этапе.

## Общие ограничения (действуют без изменений с M0)

- Схема базы меняется **только** новой версионированной миграцией в
  `listam/migrations/`. В M3.5 миграция одна — **012** (фаза 3).
- Новый метод порта — это новый контрактный тест в `tests/contracts/`.
- Ни один аккаунт, путь, ключ, идентификатор и имя адаптера не зашит в код:
  внешнее — за портом, выбор — в конфиге, секреты — только в `.env`,
  подключение — в `listam/wiring.py`. Это касается и расписания: путь к
  интерпретатору и к проекту вычисляется в момент установки, а не пишется
  в README и не хранится в репозитории.
- Все отметки времени в базе — UTC. Человеческое время (расписание, шапка
  дайджеста) — в часовом поясе из конфига.
- **Query-параметры фильтров list.am запрещены robots.txt.** Лента — только
  путевая пагинация, объявление — только `/item/<id>`.
- **Никакого массового обхода страниц объявлений.** Страница открывается
  только для кандидата под живую заявку, с паузой из конфига и потолком
  открытий за прогон. Открытая страница кэшируется в базе.
- Пороги не поднимаются, чтобы тест позеленел. Исключение одно — фаза 4:
  её предмет и есть настройка балла, и каждое изменённое число приходит
  с замером, который его обосновал.
- Ноль в пороге значит «ноль», выключается `null`. Бессмысленное значение —
  отказ кодом 2 на входе, и в командной строке, и в конфиге.
- След звонка (`matches.status`, `matches.reject_reason`) пишет только
  человек — теперь командой `mark` (фаза 6). `MATCH_COMPARED` не расширяется.
- Тесты — только `.venv/Scripts/python.exe -m pytest -q`; прогон CLI из
  скрипта — только с `PYTHONIOENCODING=utf-8`.
- Агент сам на list.am не ходит (WebFetch и подобное): `robots.txt` сайта
  закрывает его краулеры целиком. Страницы берёт только инструмент, своим
  `Fetcher`.

## Принятые решения (в фазах не пересматриваются)

1. **Первым идёт боевой запуск на нынешнем коде, а не последним шагом.**
   Каждый день без обхода — потерянная история цен, а балл без живых заявок
   настраивать не на чем. Планировщик включается в фазе 1; неделя приёмки
   считается в фазе 7, когда все доработки на месте.
2. **Боевая база начинается с чистого полного обхода.** Восстановленные из
   `.xlsx` базы приёмки M3 — стенды, а не история: `first_seen` и
   `price_history` в них выдуманы восстановлением. Боевая база получает своё
   имя файла (`listam-prod.sqlite`), чтобы dev-прогоны на той же машине не
   делили с ней рабочую копию `./data/listam.sqlite`.
3. **Расписание описано в конфиге, а исполняется одной командой.**
   `listam cycle <имя>` выполняет шаги цикла из `schedule.cycles` по порядку,
   как `&&`: первый ненулевой код — стоп. Системному планировщику достаётся
   одна строка на цикл. `listam schedule install|remove|show` сам пишет
   задачи `schtasks` (Windows) или строки `crontab` (Linux, с `xvfb-run`) по
   тому же конфигу. Переезд на Linux — `git clone`, `.env`, `schedule install`.
4. **Цикл не тревожит по пустякам и не молчит о главном.** Замок занят
   (часовой пришёлся на ночной) — цикл пропущен, строка в логе, код 0.
   Упавший шаг — одна строка брокеру в чат «⚠️ listam: часовой цикл не
   прошёл — …», не чаще `schedule.alert_every_hours`. Каждый цикл пишет лог
   в `schedule.log_dir`: при запуске по расписанию вывод иначе пропадает.
5. **Пустое «звони сейчас» не шлётся.** Событий в окне нет — сообщения нет,
   строка в журнал пишется (окно сдвигается). Иначе расписание шлёт брокеру
   24 сообщения «событий нет» в сутки (открытый вопрос 2 приёмки M3).
6. **Вёрстка — строго по пункту 8 анализа.** Карточка из трёх строк, словарь
   значков, `parse_mode: HTML`, ссылка словом «Открыть», превью выключено,
   `<`, `>`, `&` экранированы, разделитель `·`, резать только между
   карточками, каждое продолжение — с шапкой заявки. `--dry-run` и журнал
   отправок получают простой текст без тегов. Новых значков нет: словарь
   закрыт.
7. **Сообщение — структура, а не строка.** Вёрстка собирает `Message`
   из разделов (шапка, карточки, хвост), и порт `Notifier` принимает его
   целиком: резать между карточками может только тот, кто знает, где карточки.
   HTML и простой текст — два рендера одной структуры.
8. **Раздел «только закрытия» не занимает сообщения.** Закрытия уходят
   строкой в сводку дайджеста: «R-51 · Клиент 51 … ❌ 1». Отдельного
   сообщения на заявку без звонков нет (открытый вопрос 1 приёмки M3).
9. **Воронка решает, есть ли матч, а не только его балл.** Заявке нужны
   поля страницы (в её `must_have` / `nice_to_have` есть слово из словаря) —
   объявление без открытой страницы в `matches` **не пишется**: оно кандидат
   и ждёт шага `pages`. Страница открылась — ближайший подбор создаёт матч
   с `first_matched_at` в своём окне, и «звони сейчас» получает его как
   новое. Так в уведомление попадает только то, что прошло оба сита, и ни
   одно событие не теряется между шагами. Заявке без таких слов страницы
   не нужны вовсе, и запросов к сайту ради неё нет.
10. **Словарь пожеланий живёт в конфиге.** Слово брокера → поле страницы
    и допустимые значения (`funnel.wishes`). Неизвестное слово в `must_have` —
    отказ строки заявки с названным словом (как бюджет «примерно 100к»):
    жёсткий критерий наугад не истолковывается. Неизвестное слово
    в `nice_to_have` — строка ⚠ в отчёте `requests`, заявка читается.
11. **`must_have` — жёсткий критерий, `nice_to_have` — седьмой фактор
    `wishes`.** Поле известно и не подходит — отказ со словом («тип дома»).
    Страница открыта, а поля на ней нет — не отказ: узнать больше нечем,
    брокер уточнит звонком. Фактор `wishes` — доля выполненных пожеланий
    среди тех, чьё поле известно; нет ни одного известного — фактор уходит
    из знаменателя, как и остальные шесть.
12. **Причина «страница не открыта» не закрывает старый матч.** Как и снятое
    с ленты: проход его не видел, а это не «видел и не подтвердил».
13. **Страница открывается повторно, только когда объявление изменилось.**
    Сменилась сырая цена или объявление вернулось на ленту после
    `fetched_at`. Неудачное открытие повторяется до `funnel.max_attempts`,
    дальше поле считается неизвестным. Снятая страница помечается и не
    открывается больше никогда.
14. **Матч помнит, откуда он родился: `matches.origin`.** `market` — его
    принёс рынок (новое, подешевевшее, вернувшееся объявление). `request` —
    его принесла заявка: новая или правленая заявка прошла по всей базе.
    «Звони сейчас» берёт только `market`: сотни матчей новой заявки — это
    первичная подборка, а не повод звонить в этот час. Она уходит в вечерний
    дайджест разделом «первичная подборка: N лучших из M». Колонка пишется
    при вставке и в `MATCH_COMPARED` не входит.
15. **Отказ клиента сужает заявку в базе, а не в таблице.** Таблицу заявок
    ведёт брокер, и синхронизация её не перезаписывает. `mark … rejected
    --reason «первый этаж»` пишет исключение в `request_exclusions`, а
    подбор читает его как ещё один жёсткий критерий. Отвергнутая квартира
    (кластер) исключается всегда, даже если причина не из словаря.
    `mark … new` откатывает отметку вместе с её исключениями.
16. **`find` — это заявка, которую не записывают.** Флаги команды
    собираются в `Request` тем же разбором, что строка CSV, и оцениваются
    тем же скорингом. Поле страницы неизвестно — строка говорит об этом,
    а `--open N` открывает страницы лучших N с потолком из конфига.
17. **Живые проверки через Playwright планируются, но не исполняются.**
    Их список ведётся в разделе «Долги» плана; прогоняет их пользователь
    отдельно. Отправлять в Telegram при исполнении можно, читать отправленное
    обратно — нет.
18. **Реальных заявок у исполнителя нет — есть пример.** План несёт три
    синтетические заявки; фазы, которым нужны живые, работают на них
    и записывают замер как предварительный. Реальные заявки — долг
    пользователя Д-1; когда они придут, замеры фазы 4 повторяются.

## Архитектура

```
Лента list.am ──scrape──► listings ──match (грубое сито)──► кандидаты
                                                    │ нужна страница?
                                   нет ─────────────┤
                                                    ▼ да
                              pages: /item/<id>, пауза, потолок ──► listing_pages
                                                    │
                          match (тонкое сито: must_have, wishes, исключения)
                                                    ▼
                         matches (origin, первичная подборка отдельно)
                                                    ▼
             layout.Message ──► Notifier ──► Telegram HTML | stdout простой текст
```

Новые модули:

| Файл | Ответственность |
| --- | --- |
| `listam/schedule.py` | цикл из конфига, лог, тревога, генерация задач `schtasks` / `crontab` |
| `listam/layout.py` | вёрстка по пункту 8: `Message`, `Section`, карточка, два рендера |
| `listam/parsers/item_page.py` | разбор страницы объявления в `PageFields`. Чистая функция |
| `listam/domain/wishes.py` | словарь пожеланий: слово → условие на поле; проверка условия |
| `listam/pages.py` | шаг воронки: кто кандидат, что открыть, пауза, потолок, кэш |
| `listam/find.py` | быстрый поиск по базе |
| `listam/feedback.py` | отметки `mark` и исключения из отказов |

## Миграция 012

Единственная правка схемы, версия 11 → 12, делается в фазе 3.

```sql
CREATE TABLE IF NOT EXISTS listing_pages (
    listing_id      TEXT PRIMARY KEY,
    fetched_at      TEXT,
    status          TEXT NOT NULL,      -- ok | gone | failed
    attempts        INTEGER NOT NULL DEFAULT 0,
    price_raw       TEXT,               -- цена карточки в момент открытия
    fields          TEXT,               -- JSON: PageFields
    parser_version  INTEGER NOT NULL DEFAULT 1,
    error           TEXT
);

CREATE TABLE IF NOT EXISTS request_exclusions (
    id              INTEGER PRIMARY KEY,
    request_id      INTEGER NOT NULL,
    kind            TEXT NOT NULL,      -- cluster | first_floor | last_floor | district | <поле страницы>
    value           TEXT,
    reason          TEXT,               -- слова брокера как есть
    match_id        INTEGER,            -- какая отметка его породила: откат снимает её исключения
    created_at      TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_exclusions_request ON request_exclusions(request_id);

ALTER TABLE matches ADD COLUMN origin TEXT;   -- market | request; NULL — до миграции
```

HTML страницы в базе не хранится: разобранные поля — да, сырьё — нет.
Сырьё для отладки кладётся в `scrape.pages_dir` только флагом `pages --keep-html`.

## Порты и адаптеры

| Порт | Что меняется | Контрактный тест |
| --- | --- | --- |
| `Notifier` | `send(message: Message, to=None)` вместо `send(text)`; `describe()` без изменений | `tests/contracts/test_notifier_contract.py` переписывается под `Message` |
| `Database` | `get_page`, `save_page`, `pages_for(ids)`, `listings_paged_since(since)`; `add_exclusions`, `exclusions_for(request_id)`, `drop_exclusions(match_id)`; `upsert_matches` пишет `origin` при вставке | `tests/contracts/test_database_contract.py` дополняется |
| `Fetcher` | без изменений: страница объявления берётся тем же `get(url)` | существующий |

`listings_touched_since` включает объявления, чья страница открыта после
отметки: иначе `match --new` не узнает, что кандидату пора стать матчем.

## Конфиг

```yaml
locale:
  timezone: Asia/Yerevan        # человеческое время: расписание, шапка дайджеста

schedule:
  log_dir: ./data/logs
  keep_logs_days: 14
  task_prefix: listam           # имя задач в schtasks, метка в crontab
  alert_on_failure: true
  alert_every_hours: 6
  linux_xvfb: true              # на Linux цикл заворачивается в xvfb-run -a
  cycles:
    hourly:  {every_minutes: 60, steps: ["scrape --fresh", "pages", "match --new", "notify --hot"]}
    nightly: {at: "04:00", steps: ["scrape", "pages", "match --all", "notify --feed"]}
    evening: {at: "20:00", steps: ["notify --digest"]}

funnel:
  delay_seconds: 5              # пауза между страницами объявлений — больше, чем у ленты
  max_opens_per_run: 30         # потолок открытий за прогон
  find_max_opens: 20            # потолок для find --open
  max_attempts: 3
  wishes:                       # слово брокера → условие на поле страницы
    ремонт:     {field: renovation, any_of: [cosmetic, euro, designer]}
    евроремонт: {field: renovation, any_of: [euro, designer]}
    камень:     {field: building_type, any_of: [stone]}
    монолит:    {field: building_type, any_of: [monolith]}
    не панель:  {field: building_type, none_of: [panel]}
    балкон:     {field: balcony, is: true}
    лифт:       {field: elevator, is: true}

feedback:
  reasons:                      # слова отказа → что исключить из заявки
    первый этаж:    {exclude: first_floor}
    последний этаж: {exclude: last_floor}
    район:          {exclude: district}
    тип дома:       {exclude: building_type}
    ремонт:         {exclude: renovation}

notify:
  layout:
    score_green: 80             # 🟢 от этого балла; 🟡 — от match.thresholds.hot
  feed:
    enabled: true
    gem_percent: 15             # 💎 — дешевле медианы района хотя бы на столько
```

Имена полей страницы (`renovation`, `building_type`, …) и их значения —
**предварительные**. Их фиксирует разведка фазы 3 по 2–3 настоящим
страницам, и словарь правится под то, что реально есть на сайте.
Шаги `pages` появляются в циклах только в фазе 3; до неё циклы идут без них.

`match.weights` получает седьмой фактор `wishes` (фаза 3). Проверка «названы
все факторы» остаётся: без `wishes` в конфиге — отказ на входе.

## Форма сообщения

Строго по пункту 8 анализа. «Звони сейчас» — по сообщению на заявку:

```
🔥 ЗВОНИ СЕЙЧАС · R-4 · Клиент 4
Канакер-Зейтун · 2 комн. · 80–110 м² · до $175 000
━━━━━━━━━━━━━━━

🆕 $165 000 · 100 м² · $1 650/м² (−12% к району)
📍 Канакер-Зейтун, ул. Азатутян · этаж 5/9
👤 Собственник · 🟢 балл 82 · 🔗 Открыть

➕ ещё 12 вариантов — в дайджесте вечером
```

Дайджест — сводка отдельным сообщением, потом по сообщению на заявку
с событиями. Заявка, у которой только закрытия, есть в сводке и не получает
своего сообщения (решение 8). Первичная подборка новой заявки — раздел
дайджеста с шапкой «📋 … первичная подборка: 12 лучших из 495» (решение 14).
Лента — `🗞 НА ЛЕНТЕ ЗА СУТКИ`, счётчики, строки 💎.

Цена — жирным, ссылка — `<a href="…">Открыть</a>`, превью —
`link_preview_options: {is_disabled: true}`. Исключения заявки видны во
второй строке шапки словами: «· без 1-го этажа, без панели».

## Ошибки и отказы

| Ситуация | Поведение |
| --- | --- |
| Замок занят в начале цикла | цикл пропущен, строка в логе, код 0, тревоги нет |
| Шаг цикла вернул не 0 | остальные шаги не идут, код шага, тревога (не чаще `alert_every_hours`) |
| Тревога не ушла (сеть) | строка в логе; цикл не падает второй раз |
| `pages`: Cloudflare, таймаут | `attempts + 1`, повтор в следующем прогоне; код 1, если не открылась ни одна из запрошенных |
| `pages`: страница снята (404, «объявление удалено») | `status = gone`, больше не открывается |
| `pages`: поле не разобралось | поле неизвестно; прогон не падает; доля неразобранных — строка в отчёте |
| `robots.txt` запрещает `/item/` для `*` | фаза 3 встаёт и спрашивает пользователя |
| Неизвестное слово в `must_have` | отказ строки заявки с названным словом |
| `mark` на матч, которого нет | код 1, «у заявки R-4 нет матча на 24254997 и его кластер» |
| `schedule install` на неизвестной платформе | код 2 |
| Сообщение длиннее 4 096 | режется между карточками, продолжение — с шапкой заявки |

## Приёмка M3.5

Фаза 7. Неделя — это семь календарных суток после того, как фазы 1–6 влиты
и задачи расписания переустановлены.

1. **Сама:** в `runs` за 7 суток — часовые обходы не меньше чем в 90 % часов,
   ночной полный — 7 из 7 (или каждый пропуск объяснён тревогой в чате
   и строкой лога). Ни одного ручного запуска боевых команд за неделю.
2. **Единицы, а не сотни:** по журналу отправок — у каждой живой заявки
   в 95 % сообщений «звони сейчас» не больше `notify.hot.per_request`
   событий в окне, медиана — не больше 3.
3. **За секунду понятно:** вёрстка — по пункту 8, проверено тестами
   рендера; глазами в чате — долг пользователя (решение 17).
4. **Воронка вежлива:** за неделю открыто страниц не больше
   `max_opens_per_run × число прогонов`, ни одной страницы вне кандидатов.
5. `doctor` на боевом конфиге — без «СБОЙ»; батарея зелёная.

Каждое число отчёта приходит с командой, которая его напечатала.

## Что в M3.5 не входит

- Google Drive и Google Sheet вживую — M3.6 (решение пользователя).
- Участники, группы, назначения, бот по приглашению — M3.6.
- Телефоны, подборка для клиента, EUR и RUB — M4. Аналитика цен — M5.
- Отметки из Telegram (кнопки, ответы боту) — M3.6 или M5: бот пока только
  отправляет.
- Шлифовка, которую брокер не заметит: `kind: none` печатает «Событий: 0»
  (открытый вопрос 5 приёмки M3), живые проверки L-1, H-4, H-5 (перенесены
  в долги пользователя), слияние журналов двух копий.
- Массовое открытие страниц «про запас» и `find --open` без потолка.
