# План: несколько брокеров на одном сервере

> **Статус: отложено.** В роадмап не входит, сейчас не делается. Когда брать
> в работу, решено отдельно. Условие для старта: listam уже работает на Linux-VPS
> (`docs/переезд-на-linux.md`), и для одного брокера всё стабильно.

## Цель

Один сервер и один обходчик list.am обслуживают нескольких брокеров. У каждого
брокера свои заявки, матчи, отметки, настройки подбора и свой чат в Telegram.
Позже у каждого появится вход в веб-интерфейс.

**Принцип: обходчик один, даже на пилоте.** Лента list.am одна для всех, поэтому
второй обход ничего нового не принесёт. Зато с ним вдвое вырастет нагрузка на
сайт, вдвое чаще будет срабатывать проверка Cloudflare и вдвое больше браузеров
Chromium будет жить в памяти VPS. Отдельная копия listam на каждого брокера не
рассматривается.

## Что общее, а что у брокера

Разбор по текущей схеме базы (версия 11, `listam/migrations/`):

| Таблица | Чья | Почему |
| --- | --- | --- |
| `listings` | общая | лента одна; кластеры (`cluster_id`) тоже общие |
| `price_history` | общая | история цены не зависит от брокера |
| `contacts` | общая | контакт продавца один |
| `listing_pages` | общая | страница, открытая под заявку одного брокера, пригодится другому |
| `runs` | общая | журнал обходов ленты |
| `requests` | брокера | заявки его клиентов |
| `matches` | брокера | подбор, баллы, отметки `called` / `rejected` |
| `request_exclusions` | брокера | исключения из отказов его клиентов |
| `notifications` | брокера | журнал отправок в его чат; окна `hot` / `digest` / `feed` у каждого свои |

Настройки делятся так же:

| Общие (`config/prod.yaml`) | Брокера (`config/brokers/<id>.yaml`) |
| --- | --- |
| `scrape`, `rate`, `validate`, `coverage` | `requests` (CSV или Google Sheet) |
| `storage`, `locale`, `schedule` | `match` (веса, пороги, растяжка бюджета) |
| `funnel.delay_seconds`, `funnel.max_opens_per_run` (общий потолок) | `funnel.wishes` |
| `match.cluster` (кластеры общие) | `feedback.reasons` |
| | `notify` (включённые сводки, вёрстка, `chat_id`) |

## Решение по базе: общая база и отдельная база на брокера

```
data/store/
  market.sqlite            ← listings, price_history, contacts, listing_pages, runs
  broker-anna.sqlite       ← requests, matches, request_exclusions, notifications
  broker-karen.sqlite
```

Команда брокера открывает свою базу и подключает общую:
`ATTACH 'market.sqlite' AS market`. SQLite ищет таблицу без префикса сначала
в своей базе, потом в подключённых. Поэтому запросы вида
`matches JOIN listings` работают без переписывания.

Почему не столбец `tenant_id` во всех таблицах брокера:

* **Изоляция по построению.** Если в одном запросе забыть `WHERE tenant_id = ?`,
  брокер увидит чужих клиентов. С отдельными файлами так ошибиться нельзя.
* **Уход брокера** сводится к удалению одного файла. Бэкап и перенос тоже делаются
  по файлу на брокера.
* **Меньше правок в коде:** запросы остаются прежними, меняется только то, как
  открывается база.

Цена решения: SQLite не проверяет внешние ключи между файлами
(`matches.listing_id` → `listings.id`). Объявления не удаляются, только
помечаются `gone`, так что для нас это не опасно. При переходе на Postgres
(см. «Потом») этой схеме соответствует схема базы на брокера плюс общая схема
`market`.

## Цикл

Один процесс, одна задача `cron` на цикл, один замок:

```
cycle hourly
  1. scrape --fresh                              ← market, один раз
  2. pages                                       ← кандидаты всех брокеров, общий потолок
  3. для каждого брокера: requests → match --new → notify --hot
```

* Сбой шага у одного брокера (битый Google Sheet, чат недоступен) не
  останавливает остальных. Тревога уходит **оператору**, а не брокеру.
* Сбой общего шага (`scrape`) останавливает цикл целиком, как сейчас.

### Воронка (`pages`) на несколько брокеров

* Кандидаты собираются по всем брокерам, **без повторов**: одно объявление
  открывается один раз, даже если подходит троим.
* Потолок `funnel.max_opens_per_run` общий, чтобы нагрузка на list.am не росла
  с числом брокеров. Места делятся поровну по кругу: сначала лучший кандидат
  каждого брокера, потом второй, и так далее. Брокер с 50 заявками не должен
  забирать все места у брокера с пятью.

## Telegram

* **Один бот** (`TELEGRAM_BOT_TOKEN` в `.env`) и отдельный `chat_id` у каждого
  брокера в его файле настроек. Отдельный бот нужен только ради своего имени и
  аватарки, это можно решить потом.
* **Чат оператора** (`OPERATOR_CHAT_ID`) получает тревоги о сбоях, общих и
  по каждому брокеру. Брокер получает только свои сводки.

## Фазы

1. **Настройки.** Разделить конфиг на общий и файлы `config/brokers/<id>.yaml`.
   Загрузчик собирает конфиг брокера как общий плюс его файл. Если брокер
   переопределяет общий ключ (`scrape`, `storage`), это отказ на входе.
2. **База.** Миграции делятся на два набора: `market` и `broker`. Открытие
   базы брокера с `ATTACH`. Синхронизация с хранилищем
   (`take_the_fresher_copy`) и бэкапы работают по каждому файлу.
3. **CLI.** Команды брокера (`requests`, `match`, `matches`, `mark`, `notify`,
   `find`, `export`) получают `--broker <id>`, без него это отказ, если брокеров
   больше одного. Общие команды (`scrape`, `recheck`, `cluster`) работают без
   флага. `cycle` проходит по всем брокерам.
4. **Воронка.** Кандидаты без повторов и деление потолка по кругу.
5. **Уведомления.** `chat_id` берётся из настроек брокера, чат оператора
   используется для тревог.
6. **Переезд текущей базы.** Разовая команда: `listam-prod.sqlite` делится на
   `market.sqlite` и `broker-<первый>.sqlite`. Сначала проверка на копии,
   потом на боевой базе, со старым файлом рядом.
7. **Новый брокер.** Команда `broker add <id>` создаёт файл настроек из образца
   и пустую базу, `doctor --broker <id>` проверяет таблицу заявок и чат.
8. **Приёмка.** Два брокера на боевом сервере, одна неделя:
   * обходов ленты столько же, сколько при одном брокере;
   * тест изоляции: матчи, отметки и сводки брокера A никогда не попадают к B;
   * сбой таблицы заявок у A не мешает B получать сводки;
   * общий потолок воронки соблюдается, места делятся поровну.

## Открытые вопросы

* `match --new` берёт «что тронулось с начала прошлого прогона». Прогоны общие,
  а подбор у каждого брокера свой. Окно, скорее всего, нужно считать от
  прошлого подбора этого брокера, а не от прошлого обхода. Сверить, когда
  дойдём до фазы 3.
* `notify --feed` (💎 дешевле медианы района) не зависит от заявок. Слать его
  каждому брокеру или сделать тумблером в настройках брокера?
* `export` отдаёт брокеру лист «Объявления» целиком, а лист «Матчи» только
  его собственный?
* Сколько брокеров потянет VPS: подбор по всем заявкам в ночном цикле растёт
  линейно с их числом. Замерить на пилоте.

## Потом (не в этом плане)

* **Веб-интерфейс** (M5 роадмапа): ввод заявок, матчи, отметки, аналитика.
  Вход по логину, брокер видит только свою базу. Домен с HTTPS через Caddy.
* **Postgres** вместо SQLite, когда интерфейс и несколько брокеров начнут
  писать одновременно. Схема `market` плюс схема на брокера.
* **Бэкапы вне сервера:** ежедневная выгрузка файлов базы во внешнее хранилище.
* **Другие сайты и страны:** нужен свой адаптер парсера под каждый сайт. Это
  отдельный план.
